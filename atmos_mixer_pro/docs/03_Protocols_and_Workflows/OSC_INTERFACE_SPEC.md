# OSC 인터페이스 규격 (초안)

> 상태: **규격 확정, 구현 전**. 2026-11-12 작성·5절 사용자 확정. 이 문서는 문서만 바꾸며 코드는 그대로다.
> 근거: 안정성 검증 프로젝트 결정(`HANDOFF.md` 확정된 결정·남은 일 16), 사건 로그·`EngineDown` 상태 값(PR Apejean/Atmos#86).

## 1. 목적과 원칙

The Awesome은 미리 만든 PCM을 안정적으로 분배·운영하는 프로그램이다. 외부 장비(큐 컨트롤러, 방탈출 제어기 등)가 OSC로 재생을 시킨다. 사람이 없는 무인 운영이 기본이다.

1. **받는 쪽 주소는 지금 그대로다.** 방·트랙마다 설정에 적은 주소를 글자 그대로 맞춘다(`osc/router.rs`). 이 규격은 받는 쪽을 바꾸지 않는다.
2. **새로 더하는 것은 앱이 보내는 신호(응답·상태)와 조회뿐이다.** 새 주소는 `/awesome/...` 아래에 둔다.
3. **응답은 재생을 방해하지 않는다.** 보내기가 막히거나 실패해도 오디오 경로·명령 처리에 영향이 없다. 송신은 엔진·오디오 스레드가 아닌 별도 스레드에서 한다(오디오 스레드 3법칙).
4. **UDP 최선 전달이다.** 재전송·순서 보장·인증·암호화는 하지 않는다(현장 내부망). 빠진 응답은 상태 조회로 보완한다.
5. **복구 구조와 맞춘다.** 엔진 상태는 `Running / WaitingForDevice / Failed / StoppedByUser`(`HANDOFF.md` 확정된 결정). 장치가 없을 때 들어온 재생 명령은 쌓지 않고 버린다.

## 2. 받는 쪽 (현행, 변경 없음)

| 항목 | 현재 동작 |
|---|---|
| 주소 | 설정의 `play_osc_address`·`stop_osc_address`(트랙), `clear_osc_address`(방), `theme_start_osc_address`, `system_reset_osc_address`. 글자 그대로 일치 |
| 트리거 조건 | 인자가 없으면 트리거(주소만 보내는 QLab·Companion 형식, 작업 A로 코드를 맞춤). Float > 0, Int > 0(64비트 Double·Long 포함, 0보다 클 때), Bool true, 문자열 등 그 밖의 형식도 트리거. 숫자 0(32·64비트 모두)과 Bool false는 무시(버튼을 뗄 때 보내는 값). 여러 인자는 하나라도 조건을 만족하면 트리거 |
| 디바운스 | 같은 주소는 250 ms 안에 다시 오면 무시(`osc/debouncer.rs`) |
| 겹친 주소 | 마지막에 등록된 하나만 반응, 로그에 남김 |
| 미등록 주소 | 무시하고 로그 `사건: osc_unregistered addr=…` (PR #86) |
| 포트 열기 실패 | 로그 `사건: osc_bind_failed port=… error=…` (PR #86) |

방 볼륨 OSC는 쓰지 않는다(2026-10-10 사용자 결정).

## 3. 앱이 보내는 신호 (신규)

### 3.1 응답 목적지

- 설정에 **응답 목적지 목록**(IP·포트, 여러 개)과 켜기/끄기를 둔다. 목록이 비면 아무것도 보내지 않는다(지금 동작과 같음).
- 명령을 보낸 쪽 주소로 자동 회신하지 않고 **설정의 목록으로만** 보낸다. 무인 운영에서 응답 경로가 예측 가능해야 하기 때문이다. 시작 신호·상태 변화처럼 앱이 먼저 보내는 신호에는 "보낸 쪽"이 없고, 큐 장비·쇼 컨트롤러는 임시 포트에서 보내는 일이 많아 발신 포트로 회신하면 닿지 않을 수 있다. *(결정 ①)*
- 목적지는 **IP 숫자만** 받는다(DNS 이름 없음: 무인 운영 중 이름 풀이 지연·실패를 피한다).
- **브로드캐스트 주소는 받지 않는다**(Windows는 `SO_BROADCAST`가 필요하고 망 전체에 흐른다).
- 목록은 **최대 8개**. 잘못된 항목은 불러올 때 건너뛰고 로그에 남긴다.
- 상태 조회(3.6)의 답도 이 목록으로만 간다. **목록에 없는 장비가 물으면 답이 없다.**
- 나중 후보(지금은 넣지 않음): 목적지마다 "보낸 쪽에도 회신" 켜기.
- 보내는 소켓은 받는 소켓과 **따로** 만든다. Windows UDP에서는 상대 포트가 닫혀 있으면 소켓이 `WSAECONNRESET`을 겪으므로, 받는 소켓과 섞으면 수신이 끊길 수 있다.
- 보내기 실패는 로그(`사건: osc_send_failed dest=… error=…`)만 남기고 무시한다. 같은 실패는 1분에 한 번만 남긴다.

### 3.2 시작 신호

`/awesome/status/boot` — 앱이 켜지고 엔진 상태가 정해진 직후 보낸다. UDP라 1초 간격으로 3회 반복하고, 받는 쪽은 boot id로 중복을 거른다. *(결정 ③)*

| 인자 | 형식 | 설명 |
|---|---|---|
| 1 | string | 앱 버전 |
| 2 | string | 엔진 상태(`Running` / `WaitingForDevice` / `Failed` / `StoppedByUser`) |
| 3 | string | 열린 오디오 장치 이름(없으면 빈 문자열) |
| 4 | string | 시작 종류: `manual`(사람이 켬) / `logon`(로그인 자동 실행) / `relaunch`(감시 프로그램이 다시 띄움) |
| 5 | int | 이어 재생한 트랙 수(0이면 이어 간 것 없음) |
| 6 | string | boot id(시작 시각 unix ms 문자열) |

앞 세 인자의 순서는 고정이다. 장비는 시작 종류로 "아침 정상 시작"과 "충돌 복구"를 구분하고, 이어 재생 수로 큐를 다시 보낼지 정한다.

외부 장비는 앱이 다시 시작됐음을 이 신호로 안다(앱 재시작을 모르면 다음 큐까지 빈다는 문제를 푼다). 재시작 뒤 이어 재생하지 않는 트랙은 남은 길이가 짧은 비루프뿐이다(규칙은 `HANDOFF.md` 확정된 결정 참고). 장비는 이 신호를 받고 필요한 큐를 다시 보낼지 판단한다.

### 3.3 엔진 상태 변화

`/awesome/status/engine` — 엔진 상태가 바뀔 때마다 보낸다.

| 인자 | 형식 | 설명 |
|---|---|---|
| 1 | string | `Running` / `WaitingForDevice` / `Failed` / `StoppedByUser` |
| 2 | string | 짧은 원인(없으면 빈 문자열). 사건 로그·배너의 `EngineDown:<원인>`과 같은 문자열 |

현재 코드의 상태 문자열(`Running`·`Failover`·`Stopped`·`HotReloading`·`EngineDown:<원인>`)과의 대응은 유지 스레드와 하트비트 상태값을 구현할 때(안정성 3단계) 확정한다. 그 전에는 이 신호를 구현하지 않는다.

### 3.4 명령 응답

주소 `/awesome/reply`. 외부 명령을 하나 처리할 때마다 보낸다.

| 인자 | 형식 | 설명 |
|---|---|---|
| 1 | string | 받은 OSC 주소 |
| 2 | string | 단계: `ack` / `started` / `rejected` |
| 3 | string | 이유 코드(`ack`·`started`는 빈 문자열) |

- `ack`: 주소가 등록되어 있고 트리거 조건·디바운스를 통과해 처리하기로 했다.
- `started`: 재생 명령이 엔진 명령 큐에 실제로 들어갔다. 소리가 나기 시작했다는 뜻이 아니라 **엔진이 받았다**는 뜻이다(큐 이후 시작 시점은 4절 한계 참고).
- `rejected` 이유 코드:

| 코드 | 의미 |
|---|---|
| `unregistered` | 등록되지 않은 주소 |
| `gated` | 활성 방이 아니라 막힘(`check_gating`) |
| `engine_waiting` | 엔진이 장치를 기다리거나 실패 상태라 버림 |
| `file_missing` | 음원 파일을 못 찾음 |
| `exhibition_ignored` | 전시 모드라 방 비우기를 무시함 |

디바운스에 걸러진 중복 신호에는 응답하지 않는다.

### 3.5 재생 끝 신호 (비루프 한정)

`/awesome/finished` — 비루프 트랙이 끝까지 재생되어 끝났을 때 보낸다. 루프에는 보내지 않는다(끝이 없음). *(결정 ②)*

| 인자 | 형식 | 설명 |
|---|---|---|
| 1 | string | 방 id |
| 2 | string | 트랙 id |
| 3 | int | 재생 번호(instance id). 같은 비루프 트랙을 겹쳐 틀 수 있어 장비가 짝을 맞추는 데 쓴다 |

- **끝난 이유를 가른다.** 지금은 인스턴스가 정리 스레드로 넘어가 재생 목록에서 빠지는데, 거기서는 자연 종료·정지·방 비우기·디코더 오류가 모두 같아 보인다. 오디오 스레드가 정지 표시를 켤 때 인스턴스에 이유(`u8`: Ended / Stopped / Cleared / Error)만 적는다(할당·잠금 없음, 3법칙 안). 정리 스레드가 그 값을 읽어 **Ended일 때만** 송신 큐에 넣는다(`try_send`, 가득 차면 버리고 카운터를 올린다). 오디오 콜백에서는 보내지 않는다.
- 스트리밍 비루프는 디코더 스레드가 끝나면 자연 종료로 보이는데, 읽기 오류로 끝나도 똑같이 보인다. 스트리머에 "EOF로 끝남" 원자 플래그를 두어 오류는 Error로 가른다(거짓 `finished` 방지).
- 사용자가 정지시키거나 방을 비워서 끝난 경우에는 보내지 않는다.
- 시각은 근사다. 끝 뒤 페이드(약 300ms)와 정리 지연이 붙어 **끝난 뒤 약 0.5초 안**에 온다.
- 재시작 뒤 이어 재생하지 않는 트랙(남은 길이가 짧은 비루프)의 `finished`는 오지 않는다. **장비는 `boot`를 받으면 그 전에 시작한 트랙의 `finished`를 기다리지 않는다.**

### 3.6 상태 조회

`/awesome/query/status` (인자 없음)를 받으면 응답 목적지로 `/awesome/status/snapshot`을 보낸다.

| 인자 | 형식 | 설명 |
|---|---|---|
| 1 | string | 엔진 상태 |
| 2 | string | 짧은 원인(없으면 빈 문자열) |
| 3 | int | 재생 중 트랙 수 |
| 4 | string | 재생 중 트랙 목록(`방id/트랙id`를 쉼표로 연결, 없으면 빈 문자열). 패킷이 약 1,200바이트를 넘지 않게 자르고, 잘렸으면 끝에 `,…`를 붙인다 |
| 5 | int | 활성 처리 채널 수 |

조회 요청 자체는 디바운스 대상이 아니며 응답은 별도 스레드가 만든다. 트랙이 많으면 목록이 잘리므로 정확한 수는 인자 3으로 본다.

## 4. 한계와 하지 않는 것

- `started`는 "엔진 큐에 들어감"이다. 스트리밍 트랙은 디코더의 첫 묶음이 도착해야 소리가 나므로 실제 시작은 조금 늦을 수 있다. 정밀한 시작 시각 보고는 동기(그룹 시작) 작업과 함께 따로 설계한다.
- 타임코드(LTC/MTC) 연동, 재생 위치 연속 보고, 장비별 인증·암호화, 응답 재전송(시작 신호의 3회 반복 제외)은 이번 범위 밖이다.
- 대기 중(`WaitingForDevice`·`Failed`)에 들어온 재생 명령은 버린다. 큐에 쌓였다가 복귀 때 한꺼번에 재생되는 일이 없게 한다. 앱이 다시 시작되면 외부 장비는 `boot` 신호를 보고 필요한 큐를 다시 보낸다.
- 앱 안의 응답 목적지 목록은 `config.json` 구조 변경이다. Rust `AppConfig`와 Dart 모델을 1:1로 맞추고 Main 에스컬레이션을 거친다. FRB API 시그니처는 필요할 때만 바꾼다.

## 6. 구현 순서(제안)

1. PR #86(사건 로그·`EngineDown` 계약)을 병합한다.
2. 이 규격을 사용자가 확인한다(5절 확정).
3. 응답·시작 신호·조회를 구현한다(송신 스레드와 기존 수신 처리에서의 호출만 더함, 엔진 구조 변경 없음).
4. `status/engine`은 안정성 3단계(유지 스레드·하트비트 상태값) 뒤에 구현한다.
5. 실기: 외부 송신기로 각 응답을 확인하고, 목적지가 닫혀 있어도 수신이 끊기지 않는지(`WSAECONNRESET`)와 응답 지연이 재생에 영향이 없는지 확인한다.
