  - **자동 재실행은 앱 안에서 회복할 수 없을 때만 한다.** 장치가 없어서 못 여는 동안에는 앱을 다시 띄우지 않는다(다시 띄워도 장치가 생기지 않고 30초 찾기만 되풀이한다). 앱 안의 엔진 유지 스레드가 설정 장치를 계속 찾는다(간격 상한 예 30초). 앱 재실행 조건: 엔진 시작 호출이 돌아오지 않음(ASIO 드라이버 멈춤), 유지 스레드 멈춤, 장치는 있는데 열기가 연속 실패. 하트비트는 불리언(`engine_active`) 대신 상태값 `Running / WaitingForDevice / Failed / StoppedByUser`와 진행 카운터로 바꾼다(`WaitingForDevice`이고 카운터가 늘면 감시는 정상으로 본다. 사용자가 일부러 정지한 것을 오류로 보고 재실행하지 않기 위함). 횟수·간격은 감시의 기존 규칙을 쓴다(`supervisor/src/run.rs` `AUDIO_STALL_LIMIT` 3, `backoff.rs` 2~60초). 한도 뒤에는 앱을 띄운 채 지속 배너. 재시작·장치 찾기 30초 동안 `engine_active=false`는 정상이므로 유예가 그보다 길어야 한다. 지금 코드는 기본 장치 전환까지 실패하면 복구 스레드가 끝나 더 시도하지 않고, 앱 내부 워치독(엔진 스레드의 점검 루프)도 엔진과 함께 사라지며, 감시 프로그램은 `engine_active == false`이면 오디오 정지를 판단하지 않는다(`simple.rs` `start_audio_system`, `supervisor/src/watch.rs`).
    - **⑥ 구현(2026-11-17, PR #112, 감시 설계 `2026-10-05-crash-relaunch-supervisor-design.md` 5.3.1, 수치 사용자 확인 "이대로"):** 하트비트에 `engine_cause`(실패 원인)를 더했고, 감시가 `engine_state`·`engine_progress`·`engine_cause`를 선택 값으로 읽는다(없으면 옛 앱으로 보고 지금 규칙). 다시 띄우는 경우: `Failed(start_hung)` 바로, 대기·실패인데 진행 카운터가 90초 그대로(유지 스레드 멈춤), `Failed(open_failed)`가 2분 이어짐. 장치 대기(카운터가 늚)·`Failed(unavailable)`·`StoppedByUser`는 다시 띄우지 않는다. 엔진 상태 재실행은 오디오 멈춤과 따로 연속 3번(`ENGINE_RELAUNCH_LIMIT`)까지, Running이 보이면 초기화, 한도 뒤에는 기록만(앱 배너가 원인을 보임). 다시 띄울 때 `--auto-relaunched`라 공연을 이어 간다(장치가 없으면 ③ F2대로 들고 있다가 튼다). 감시 로그에 엔진 상태 변화를 남긴다. 시험 `supervisor/tests/rules.rs`(판단 규칙·하트비트 읽기)·`supervise.rs`(가짜 앱: 시작 멈춤 3번 뒤 멈춤·초기화, 대기는 그대로·카운터 멈춤은 다시 띄움), 앱 `test_app_signals`(키 8개). 실기(감시 + 실제 앱)는 아직 — 시작 멈춤은 실제로 만들기 어렵고, 장치 대기 중 다시 띄우지 않는 것은 설치본 감시로 확인할 수 있다.
    - **처음 상태값 `Starting`(2026-11-19 사용자 결정 "1번으로", 브랜치 `win/engine-starting-state`):** 앱을 켠 뒤 처음 엔진을 열어 결과가 나오기 전에는 `Starting`이다(하트비트·OSC 시작 신호·상태 조회). 예전 처음값 `StoppedByUser`는 ⑥ 현장 시험에서 UFX+가 꺼진 채 다시 띄워질 때 32초 동안 "사용자가 정지함"으로 보고됐다. 다시 열 때는 여전히 직전 상태를 유지한다(엔진 유지자 설계 D7). 감시는 모르는 값으로 보아 정상 처리한다(코드 변경 없음, 시험 추가).     - **장치를 다시 찾는 동안 받은 재생(2026-11-19, 검토 세션 발견, 사용자 결정 "1.3.13 전에 그 방향으로 고쳐", 브랜치 `win/keeper-queue-absorb`):** 자기 재시작이 장치를 찾는 30초 + 15초(상태 `Running`)나 사용자 재시작·재스캔 중에 받은 재생 명령이 큐에 남아, 대기로 간 뒤 장치가 돌아올 때 한꺼번에 날 수 있었다. 유지자가 대기·실패로 처음 들어갈 때 큐의 재생을 재개 항목으로 옮기고 큐·재생 목록을 비운다 — 장치가 오면 기존 이어 가기(끊긴 시간 건너뛰기, ⑦ 10초 규칙)를 탄다. 후속(검토 세션 지적 반영): 재생 목록에 남은 것만 옮김(받았다 곧 멈춘 재생은 살아나지 않음), 이미 재개 대기에 있는 루프를 다시 누른 것은 옮기지 않음(두 벌 방지), 꺼낸 명령은 별도 스레드에서 버림(유지자 잠금 밖), 재생 경로 네 곳에서 큐에 보내기 바로 앞에 재생 받기를 한 번 더 확인(파일을 읽는 동안 대기로 바뀐 재생이 남지 않게, 스트리밍은 그룹 준비 표시 앞). 남는 틈은 마이크로초.
    - **③ 구현(2026-11-14, 브랜치 `win/engine-keeper`, 설계 `docs/superpowers/specs/2026-11-14-engine-keeper-design.md`, 사용자 결정 U1~U4 "응 네가지 제안 진행해"):** 엔진 수명은 유지자 스레드 하나(`core/engine_keeper.rs`)가 맡는다. 자기 재시작의 일회성 재연결 스레드를 없앴다. 설정 장치·기본 장치(비상 전환, ⑤까지 유지)가 모두 실패하면 `WaitingForDevice`로 두고 1·2·4·8·16·30초, 그 뒤 30초마다 다시 찾는다(재시도의 장치 찾기는 5초, 첫 시작·자기 재시작은 30초 그대로). 장치는 보이는데 열기가 3번 연속 실패하면 `Failed(open_failed)`(30초마다 계속 시도), 시작 호출이 찾기 시간 + 15초 안에 돌아오지 않으면 `Failed(start_hung)`(더 시도하지 않음, 회복은 앱 재실행 — 정책은 ⑥), 이 PC에 나타날 수 없는 장치면 `Failed(unavailable)`. 사용자 정지는 `StoppedByUser`(재시도 없음). 하트비트에 `engine_state`·`engine_progress` 두 줄을 더했다(대기·실패 중 5초마다 카운터가 늚. 감시 파서는 모르는 키를 건너뛰어 감시 코드는 그대로, 정책은 ⑥).   - **재시작 때 이어 가지 않는 트랙: 무한루프가 아닌 트랙 중 남은 길이가 10초 이하인 것만 버리고 나머지는 이어 간다(사용자 결정 2026-11-10).** 엔진 재시작(`core/restart_resume.rs`)과 앱 재실행·로그인(`core/show_state.rs`) 두 경로 모두에 적용한다. 앱에는 효과음 구분이 없고 비루프 트랙에도 긴 소스가 있어(Main 확인: 이 PC 프로젝트에 비루프인데 약 10분짜리 4채널 24bit 파일이 있다) `is_loop`로 가르지 않는다. 외부 장비는 앱 재시작을 모르므로 OSC가 다시 오지 않고 다음 큐까지 빈다. **구현(2026-11-17, PR #113, 안정성 ⑦):** 판단은 `restart_resume::keep_for_resume` 한 함수다(반복은 언제나, 길이를 모르면 이어 감). 엔진 재시작 복원은 끊긴 시간만큼 건너뛴 뒤의 위치로, 앱 재실행·로그인·장치 대기 이어 가기는 저장된 위치로 잰다. 버린 트랙은 앱 로그에 남는다. 이어 갈 트랙이 모두 빠지면 아무것도 틀지 않고 활성 방만 되살린다 — 첫 방 테마로 시작하지 않는다(사용자 결정 2026-11-16). `test_restart_resume.rs`는 파일이 없는 메모리 트랙이라 길이를 몰라 단정이 그대로이고, `test_engine_keeper`의 건너뛰기 단정을 이 기준으로 고쳤다. 시험 `test_resume_tail_rule`·`test_resume_tail_all_dropped`(실제 WAV 길이).

## ⚠️ Windows 미검증 (실기에서 먼저 확인할 것)

> 읽는 법(2026-11-15): 아래 문단과 목록은 2026-10-05~07에 쓴 그대로다. 그 뒤 Windows 개발 PC(RME UFX+, ASIO)에서 빌드·실행·장치 확인을 계속해 왔다. 항목별로 확인됐는지는 각 항목의 "→ 날짜" 덧붙임과 `docs/WINDOWS_FIELD_CHECKLIST.md`의 결과 기록을 본다.

이 저장소 작업은 전부 macOS에서만 이뤄졌다. Windows용 크로스 컴파일도 막혀 있다 — `cargo check --target x86_64-pc-windows-msvc`조차 `rusqlite`(bundled sqlite3)·`dart-sys`의 네이티브 C 빌드 스크립트가 MSVC 헤더(`assert.h`, `stdlib.h`)를 못 찾아 실패한다(2026-10-01 확인). 최소 검증도 실제 Windows 컴퓨터가 있어야 한다. 이 저장소에는 Windows CI 워크플로우도 없다(`git log`로도 한 번도 존재한 적 없음) — 과거 "Windows CI 빌드 에러 수정" 커밋들은 실기에서 수동으로 잡은 것으로 보인다.

Windows 실기에서 먼저 빌드·실행해 확인해야 하는 항목:
1. **cpal 0.15.3 → 0.16.0 업그레이드**(macOS 스트림 누수 수정 목적). ASIO/WASAPI 경로는 cpal 내부 구현이 다르므로 Windows에서 컴파일·동작 여부가 전혀 확인 안 됐다. 과거에도 cpal 마이너 업그레이드에서 Windows만 깨진 이력이 있다.
2. **엔진 세대 가드**(`engine.rs` `begin_callback`/`ENGINE_GENERATION`) — 네 콜백(F32/I16/I32/U16) 전부와 Windows 전용 코드(ASIO COM 초기화 등)가 같은 함수 안에 있다. 컴파일은 될 가능성이 높지만 실기 검증은 없다.
3. **통합 테스트의 `device_name: null`(기본 장치)**. Windows는 cpal 기본 장치가 WASAPI이고 ASIO는 항상 이름을 명시해야 잡힌다(`get_hosts`의 `[ASIO]`/`[WASAPI]` 접두사 분기). 설계는 일관되지만 테스트가 Windows에서 그대로 돌아가는지는 별도 확인 필요.
4. **Flutter integration_test(app_flow_test) 자체가 macOS 전용이다.** 실행이 `-d macos`로 고정돼 있고, 스피커 탭 재현에 쓰는 `SpeakerBridge` WebView 채널은 `webview_flutter`의 macOS 구현(WKWebView)을 탄다 — Windows는 별도 플러그인(WebView2)이라 같은 방식으로 동작하는지 미확인. 재시작 감지(`err_fn`)는 `"DeviceNotAvailable"`(공통)과 `"kAsioResetRequest"`(Windows ASIO)를 둘 다 같은 `device_needs_reset` 플래그로 받게 짜여 있어, 그 이후 스냅샷·복원 로직 자체는 플랫폼 무관하게 설계됐다. 다만 Windows에서 실제로 그 경로가 타는지, WebView2로 탭이 똑같이 재현되는지는 확인된 적 없다. → 2026-10-07 Windows에서 `app_flow_test -d windows` 0~6단계 통과(통합 테스트 Windows 이식 PR #27 + 3D 뷰어 남은 일 10, 5단계 재시작 이벤트→재개 105ms).
5. **재시작 복원(ASIO/WASAPI 재기동 경로)** — 2026-10-03 구현은 macOS 실기로만 검증했다(4번 참고).
6. **절전 방지(`SetThreadExecutionState`, 2026-10-05)** — `windows` 크레이트에 `Win32_System_Power` 기능을 더했다. API 이름·시그니처는 windows 0.58 소스로 확인했지만 컴파일·동작은 미확인. 실기에서는 관리자 명령 프롬프트의 `powercfg /requests` SYSTEM 항목에 앱이 보이면 걸린 것이다.
7. **로그 내보내기 바탕화면 경로(2026-10-05)** — PowerShell로 `[Environment]::GetFolderPath('Desktop')`을 묻는다. OneDrive로 바탕화면이 옮겨진 PC에서 맞는 폴더에 저장되는지 확인 필요.
8. **installer 버전(2026-10-05)** — `installer.iss`가 빌드된 exe의 `ProductVersion`을 읽는다(ISPP `GetStringFileInfo`). exe 경로는 기존 `[Files]`와 같은 기준(스크립트 폴더)이다. 그런데 `[Files]`의 `build\...` 경로는 스크립트가 있는 `windows\` 폴더 기준이라 그대로는 파일을 못 찾을 수 있다(예전부터 그랬다). 설치 파일을 만들 때 실제로 어떻게 빌드하는지 확인 필요.

RME(ASIO MADIface USB)는 94채널에 `Analog 1 (1)`…`AES 1 (1)`…`ADAT 1 (1)`…`MADI 1 (1)` 같은 이름을 준다. 끝의 "(1)"은 RME가 여러 대를 묶을 때 쓰는 장치 번호라, 모든 채널에 같은 꼬리면 엔진이 뗀다(`strip_common_suffix`, 사용자 요청). `(1)`·`(2)`가 섞이면 장치를 가려야 하니 둔다. 엔진이 열지 않은 다른 ASIO 장치는 여전히 "Channel N"이다. 화면(Dart, macOS도 같음): 스피커 배치·스피커 속성·FX는 원래대로 `Ch-1 (Analog 1)`이다. 메인 트랙 출력과 환경설정 트랙 매핑(`buildChannelRoutingItems`)은 사용자 이름 뒤에 ` · 장치 이름`을 붙인다: `Mono (Ch-1) · Analog 1`, `Stereo (Ch-1/Ch-2) · Analog 1/2`(두 이름이 숫자 하나만 다르면 묶고, 아니면 `Analog 12 / AES 1`), `N-Ch (Ch-15~18) · ADAT 1~4`. Output Config 창은 채널 버튼(80px) 옆 이름 칸의 흐린 안내 글씨로 보인다. 이름을 모를 때의 기본값 "Channel N"은 붙이지 않는다(WASAPI는 지금과 같다). 메인 트랙 카드의 출력 드롭다운은 남은 폭을 채우고 긴 라벨을 `…`로 줄인다.

- 통합 테스트는 기계가 바쁘면(예: Claude 앱 화면이 CPU를 크게 쓸 때) VU 전달이 들쭉날쭉해진다. 5단계는 재개 대기 구간(약 100ms) 안의 표본 수가 아니라 앞뒤 0.5초 구간으로 VU 스트림이 살아 있는지 본다.
- **측정용으로 macOS 앱을 다른 홈에서 띄울 때**: `CFFIXED_USER_HOME`로 앱을 띄우면 `config.json`·상태 파일은 그 홈으로 가지만, 환경설정(SharedPreferences, NSUserDefaults)은 실제 `~/Library/Preferences/com.example.atmosMixerPro.plist`에 쓴다. 2026-10-06 측정 때 이 때문에 실제 환경설정의 `flutter.tuning_state`가 바뀌어 측정 전 백업으로 되돌렸다. 또 `defaults import com.example.atmosMixerPro`는 컨테이너(`~/Library/Containers/com.example.atmosMixerPro`)가 있으면 그쪽 plist에 쓰므로, 실제 파일을 고칠 때는 도메인 대신 plist 전체 경로를 준다. 환경설정까지 분리하는 방법은 2차 측정(2026-10-06)에서 확인했다: 릴리스 앱을 `ditto`로 복사 → `plutil`로 `CFBundleIdentifier`를 `com.example.atmosMixerPro.memdiag`로 바꿈 → `codesign --force --deep --sign -`(원본도 adhoc 서명) → `CFFIXED_USER_HOME`(파일)과 `TMPDIR`(로그·신호 파일)을 함께 주고 실행. 끝나면 `defaults delete com.example.atmosMixerPro.memdiag`로 시험 도메인을 지운다.
- **원격(TeamViewer 등)으로 앱 소리를 들을 때(2026-10-10 이 PC 확인)**: 원격 도구는 Windows **기본 재생 장치**로 나가는 소리만 보낸다. ASIO는 Windows 믹서를 거치지 않아 원격으로는 들리지 않고, WASAPI도 기본 재생 장치가 아닌 장치(예: 기본이 `Analog (3+4)`인데 앱은 `ADAT (3+4)`)로 내면 들리지 않는다. 앱 장치를 `[WASAPI] <기본 재생 장치>`로 바꾸면 들린다(그 출력의 실제 스피커에서도 소리가 난다). 원격 소리는 압축·지연이 있어 늘어짐·리버브 판단에는 쓰지 않는다. 현장 운영은 ASIO로 되돌린다.
- **OSC를 보내는 쪽이 지킬 것(2026-10-10 이 PC 확인)**: 주소는 글자 그대로(대소문자 구분) 맞아야 하고, 트리거는 0보다 큰 값을 붙여야 한다(`/room1/track1/play 1` — 값이 없거나 0이면 무시, `osc/listener.rs`). 같은 주소를 0.25초 안에 다시 보내면 두 번째는 무시한다(중복 방지). 방 비우기는 다음 방을 자동으로 활성화하고 그 방의 반복 트랙을 튼다(마지막 방이면 활성 방 없음). 테마 시작은 전체 정지 뒤 첫 방 반복 트랙, 시스템 리셋은 전체 정지다.
- **설정(AppConfig)을 일부만 바꿀 때는 `lib/core/state/config_copy.dart`의 `copyWith`만 쓴다(2026-10-11).** FRB가 만든 클래스에는 copyWith가 없어, 예전에는 화면 33곳이 칸을 하나하나 다시 적으며 전역 리버브를 0%·1.0으로, 방 카드는 OSC 허용 목록을 빈 목록으로 덮고 머리 추적 OSC 주소를 빠뜨렸다(이 세 칸은 지금 쓰는 화면·엔진이 없어 소리에는 영향이 없었다). Rust `AppConfig`에 칸을 더하면 그 파일의 `copyWith`와 `test/config_copy_test.dart`의 `full()`(기본값이 아닌 값)만 고친다. `RoomConfig`·`TrackConfig`는 지금 모든 칸이 필수라 빠뜨리면 컴파일러가 잡는다(Rust에서 `Option` 칸을 더하면 선택 칸이 되어 못 잡으니, 그때는 같은 방식의 copyWith를 만든다).
