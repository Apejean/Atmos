# Windows 현장 점검표

- 날짜: 2026-10-05 (2026-10-06 갱신)
- 대상: Windows PC(현장 PC 또는 같은 구성의 시험 PC)
- 기준(사용자 결정, 2026-10-05): **현장 PC는 Windows이고, 지금 되는 기능은 Windows에서도 동일하게 동작해야 한다. 3D 방 뷰어는 반드시 들어간다.** 메뉴 형태, 종료 경로, 절전 방지·로그 경로 구현 방식 같은 OS 고유 차이는 허용한다.
- 이 점검표의 내용은 코드를 읽어 만든 것이다. **Windows에서 실행해 본 적이 없다.** "예상"으로 적은 것도 설계상 기대일 뿐 확인된 사실이 아니다. 결과가 다르면 HANDOFF "Windows 미검증"에 적는다.
- 근거 문서: `docs/superpowers/specs/2026-10-05-crash-relaunch-supervisor-design.md`(7절), `docs/HANDOFF.md`("⚠️ Windows 미검증", "남은 일").

## 사용법

- 위에서 아래 순서로 따라 한다. 앞 절이 실패하면(빌드·설치·기동) 뒤 절은 의미가 없다.
- Windows 개발 PC의 Claude 세션으로 진행할 때는 `docs/windows/WINDOWS_HARNESS.md`를 따른다(P6이 이 점검표를 묶음으로 나눠 진행하고, 결과는 그 하네스의 RESULTS.md에 먼저 적은 뒤 결과 PR로 이 문서에 옮긴다).
- 각 항목은 `[ ]`에 결과를 적는다: `OK` / `실패(증상)` / `해당 없음`. 맨 아래 "결과 기록"에 PC 정보와 함께 정리한다.
- 로그 위치: 앱 로그 `%TEMP%\atmos_mixer_pro_logs\atmos_mixer_pro.log`(밀린 파일 `.1`~`.4`), 감시 기록 `%TEMP%\atmos_mixer_pro_logs\supervisor.log`. 신호 파일(`app.lock`, `app.pid`, `heartbeat`, `clean_exit`, `supervisor.lock`)도 같은 폴더다.
- 앱 메뉴 "Export Log"로 로그를 바탕화면에 내보낼 수 있다(아래 6절에서 이 기능 자체를 점검한다).
- 실제 오디오 장치를 쓰는 항목은 다른 프로그램이 장치를 쥐고 있지 않은 상태에서 한다(특히 ASIO는 한 번에 하나만 열린다).

## 0. 빌드와 설치

- [ ] **Windows CI 빌드.** `main`(또는 PR 트리거가 생긴 뒤의 PR)에 대한 "Build and Release" 빌드가 Windows·macOS 모두 성공한다. 8/26 이후 `cpal` 0.16(ASIO), `rusqlite` bundled, 재시작 복원, 절전 방지(`Win32_System_Power`), 새 `windows` 크레이트 기능이 Windows에서 컴파일되는 첫 확인이다. 실패하면 로그를 HANDOFF에 붙인다. → PR #8·#10(2026-10-05)에서 통과했다. 이후 `main` 대상 PR마다 자동으로 돈다.
- [ ] **설치.** `AtmosMixerPro_Setup.exe`로 설치된다. 설치된 앱의 버전과 설치 목록의 버전이 같다(installer가 빌드된 exe의 `ProductVersion`을 읽는다. `pubspec.yaml` 버전은 1.1.2). installer 스크립트의 `build\...` 경로가 `windows\` 폴더 기준이라 그대로는 파일을 못 찾을 수 있다는 HANDOFF 8번 항목도 설치 파일을 만들면서 확인한다. **설치 파일은 더블클릭으로 연다.** 관리자 승인(UAC) 창에서 "예"를 누르면 관리자 권한으로 설치된다(2026-10-23 개발 PC). PC에 따라 Windows가 관리자 권한 안내 창을 먼저 띄우기도 하는데(Inno Setup의 메시지가 아니다), 확인을 누르면 UAC를 거쳐 계속된다. 마우스 오른쪽 → "관리자 권한으로 실행"도 된다. Inno Setup 설치 파일은 일반 권한으로 시작해 스스로 관리자 권한을 요청하는 방식이라 처음부터 관리자로만 실행되게 고정할 수는 없고, 어느 쪽으로 열어도 보안 프로그램의 가로채기는 막지 못한다(아래 보안 프로그램 항목). 설치 파일은 **GitHub 릴리스의 `AtmosMixerPro_Setup_v<버전>.exe`**를 쓴다(태그를 올리면 CI가 만들어 붙인다).
- [ ] **WebView2 런타임.** 3D 방 뷰어에 필요하다. 설치 로그(`%TEMP%\Setup Log *.txt`)의 "WebView2 Runtime registered: …" 줄(등록 버전, 실제로 쓰는 버전, 설치·복구·건너뜀)과 "Prerequisite …" 줄로 본다. 설정 > 앱 목록에는 보이지 않을 수 있다(개발 PC의 제거 항목이 SystemComponent=1). Windows 10 PC에는 없을 수 있다. 설치 파일이 런타임이 없거나 번들(154.0.4258.62)보다 낮으면 오프라인으로 설치하고, 같은 버전이 손상됐으면 복구한다(2026-10-08 결정, 2026-10-11 보강). 설치 종료 코드 102면 WebView2를 쓸 수 없는 상태로 끝난 것이다(인터넷 연결 뒤 복구, 그때까지 7절에서 3D 안내가 뜨는 것이 정상).
- [ ] **앱 기동.** 앱이 뜨고 스플래시를 지나 대시보드가 나온다. 로그에 `ASIO Load Error`나 패닉이 없다.
- [ ] **서명 없는 설치 파일(사용자 결정 2026-10-08: 코드 서명 안 함, 백신 예외).** SmartScreen 창이 어떻게 뜨는지, "추가 정보 → 실행"으로 설치되는지, Defender·현장 백신이 설치 파일·앱·감시 프로그램(`atmos_supervisor.exe`)을 격리하는지 기록한다. 걸리면 앱 폴더를 예외로 넣고 다시 확인한다.
- [ ] **설치 전에 보안 프로그램 예외(2026-10-23 개발 PC에서 확인).** 현장 PC에 깔린 보안 프로그램을 모두 확인한다: 백신(Avast·AVG·알약·V3·Norton·McAfee·Kaspersky 등, Windows 보안의 Defender·SmartScreen 포함), 제3자 방화벽, 랜섬웨어 방지(Windows "제어된 폴더 액세스" 등). 서명 없는 새 실행 파일은 이런 프로그램이 지우거나, 처음 실행을 늦추거나, 샌드박스 안에서 먼저 실행한다. 설치 파일이 있는 폴더와 설치 폴더(새로 설치하면 `C:\Program Files (x86)\The Awesome`, 이름 변경 전 설치본은 `…\Atmos Mixer Pro`)를 **보안 프로그램마다** 예외에 넣고(샌드박스·행동 감시 예외가 따로 있으면 그것도) 설치한다.
  - 개발 PC(Avast·알약 설치, Avast가 방화벽 제품으로 등록)에서 본 증상: Avast가 설치 파일을 샌드박스 안에서 먼저 실행했고(AvastSvc.log "marked for virtualization"), 그 실행의 방화벽 규칙 변경은 실행 중인 방화벽에만 남고 저장된 규칙에는 남지 않았다(방화벽 이벤트 2052 삭제·2097 추가, 10-23 19:39·20:04). 검사가 끝난 뒤 실제 설치가 다시 떴다가 한 번 중단됐고(설치 로그 #003) 다음에 끝났다(#004). 두 규칙 목록이 갈라져 설치 파일의 규칙 삭제가 실패했고(netsh 종료 코드 1), 옛 규칙 "Atmos Mixer Pro OSC"가 남고 "The Awesome OSC"가 설치마다 한 쌍씩 늘었다. 그 전에는 관리자 권한을 얻지 못해 "이 프로그램을 설치할 때 관리자로 로그인해야 합니다"(10-22에는 "오류 5: 임시 디렉터리에서 파일을 실행할 수 없습니다")로 멈췄고, 새 감시·앱이 샌드박스 안에서 돌다 멈췄으며, 설치 파일이 HKCU Run 키에 쓰거나 지운 것이 실제 레지스트리에 반영되지 않았다.
  - 설치 창이 두 번 뜨거나, 관리자 승인 뒤 창이 사라지거나, 위 오류가 나오면 보안 프로그램을 의심한다. 예외를 넣은 뒤 다시 설치한다.
  - 10-24 개발 PC: Avast는 설치 파일이 실행할 때마다 임시 폴더(`%TEMP%\is-…tmp`)에 새 이름으로 푸는 `AtmosMixerPro_Setup.tmp`를 샌드박스에 넣었다. 그 안의 실행이 "이 프로그램을 설치할 때 관리자로 로그인해야 합니다"와 "내부 오류: CallSpawnServer: Unexpected response: $0"을 냈고, 약 25초 뒤 Avast 검사가 끝나면 실제 설치가 정상으로 돌았다. Avast가 설치 파일(`AtmosMixerPro_Setup.exe`)은 스스로 예외에 넣었지만 임시 파일은 경로가 매번 달라 파일 하나 예외로는 막을 수 없고, Avast가 그 파일을 해시로 예외에 넣으려다 오류 122로 실패했다. 임시 폴더 전체 예외는 만들지 않는다(사용자 결정). CallSpawnServer 오류는 설치 파일을 고쳐 없앴다(관리자 승인 전 사용자로 실행하는 단계를 없앰, 2026-10-24). 관리자 오류 창은 백신이 관리자 권한을 막아서 나므로 설치 파일로는 없앨 수 없다.
  - 10-24 개발 PC(같은 날 저녁): Avast 자동 샌드박스가 설치 결과까지 망가뜨렸다. 설치·제거 창이 두세 번씩 떴고, 설치 기록 두 개가 모두 정상인데도 설치 뒤 `data\flutter_assets`가 통째로 없어 3D 화면이 비었으며(17:5x), 완전히 지우고 새 기본 폴더 `The Awesome`에 다시 설치한 뒤에는 Avast가 그 폴더의 감시·앱을 샌드박스에 넣어 3D(WebView2)가 뜨지 않았고 이어서 `atmos_mixer_pro.exe` 자체가 폴더에서 사라졌다(19:37~19:41, 격리 기록 없음, 샌드박스에 갇힌 감시는 "파일을 찾을 수 없음"으로 계속 재시도). 예전 폴더는 10-22에 Avast가 클라우드에서 깨끗함으로 처리해 두어 문제가 없었다. Avast가 있는 PC는 설치 전에 자동 샌드박스를 "묻기"로 두거나, 설치 폴더의 `atmos_mixer_pro.exe`·`atmos_supervisor.exe`를 예외에 넣은 뒤 설치하고, 설치 뒤 설치 폴더에 두 exe와 `data\flutter_assets`가 있는지, 3D 화면이 뜨는지 확인한다.
  - 설치 뒤 확인: 설치 로그(`%TEMP%\Setup Log *.txt`)가 성공으로 끝났는지, 작업 스케줄러 "The Awesome Autostart"가 로그인한 사용자로 있는지, 방화벽 인바운드 규칙에 "The Awesome OSC" 두 개만 있고 옛 이름이 없는지(5절), 앱이 뜨고 소리가 나는지.
  - 제3자 방화벽이 Windows 방화벽 대신 켜져 있으면(Windows 보안 → 방화벽 및 네트워크 보호에 그 제품 이름이 보임) 설치 파일이 넣은 Windows 방화벽 규칙이 적용되지 않을 수 있다. 그 제품의 방화벽에서 `atmos_mixer_pro.exe`의 UDP 수신(OSC)을 허용한다.
  - Windows 보안의 "랜섬웨어 방지 → 제어된 폴더 액세스"가 켜져 있으면 문서·바탕 화면에 둔 프로젝트(.atmos, 음원, 도면)를 저장하지 못할 수 있다. 앱을 허용 목록에 넣거나 보호되지 않는 폴더(예: `D:\Shows`)에 둔다.

## 1. 로그인 자동 실행과 이어 가기 (구현 후 점검)

감시 프로그램(`atmos_supervisor.exe`)과 시작 관문이 구현된 빌드에서 한다.

- [ ] 환경설정 "로그인할 때 공연 자동 시작"이 **켜짐**(기본)일 때 PC를 다시 로그인하면 감시 프로그램이 앱을 띄우고, 저장 후 10분 안이면 멈춘 위치부터 이어 가고, 그렇지 않으면 첫 방 테마로 시작한다. 앱 로그에 어느 길로 갔는지 남는다.
- [ ] 같은 설정이 **꺼짐**일 때 로그인하면 앱이 떠서 대기한다(공연을 시작하지 않는다).
- [ ] 바로가기로 사람이 켰을 때는(`--logon`·`--auto-relaunched` 없음) 대기한다.
- [ ] **IoT 전원 — Windows 종료 명령.** 공연 재생 중 Windows 종료(또는 다시 시작) 명령으로 끈다 → 종료가 "앱이 종료를 막고 있음" 화면에서 멈추지 않고, `supervisor.log`에 종료 중 앱을 다시 띄운 기록이 없다. 다시 켜면 자동 로그인 → 감시 → 앱 → 공연 시작(위 첫 항목과 같은 길). 현장 PC는 BIOS의 전원 복구(또는 Wake-on-LAN)와 Windows 자동 로그인이 켜져 있어야 한다.
- [ ] **IoT 전원 — 전원 차단.** 공연 재생 중 전원 플러그를 뽑는다 → 다시 꽂으면(BIOS 전원 복구) 자동으로 켜져 공연이 시작된다. 꺼져 있던 시간이 10분 안이면 멈춘 위치부터, 넘으면 첫 방 테마부터다. `config.json`과 공연 상태 파일이 깨지지 않는다(둘 다 임시 파일에 쓴 뒤 바꿔 끼워 저장한다).
- [ ] **켤 때 인터페이스가 없을 때.** 인터페이스 전원이나 USB를 뺀 채 앱을 켠다 → 30초 뒤 기본 장치로 비상 전환(−40dB, 앱 로그 "비상 전환: 앱을 켤 때 …")하고 공연은 이어 간다. 인터페이스를 켜거나 꽂는다 → 몇 초 안에 그 장치로 다시 열려 원래 크기로 돌아온다(HANDOFF 확정된 결정, 2026-10-22).

## 2. 감시와 재실행 (스펙 7절)

- [ ] **작업 관리자로 강제 종료** → 몇 초 안에 다시 뜨고(`--auto-relaunched`) 공연이 멈춘 위치부터 이어진다. 위치는 최대 5초 앞일 수 있다. `supervisor.log`에 충돌과 재실행이 남는다.
- [ ] **리소스 모니터로 일시 중단** → 멈춤 판단(기본 30초) 뒤 강제 종료되고 다시 뜬다.
- [ ] **창 정상 닫기(X)** → 다시 뜨지 않고 감시도 끝난다. `clean_exit` 파일이 남고, 닫는 직후 ASIO 장치가 풀려 다른 프로그램에서 열 수 있다. 작업 관리자에 `atmos_mixer_pro.exe`가 남지 않는다. (`onWindowClose`의 엔진 정지 대기 1.5초가 ASIO 해제에 충분한지 본다.)
- [ ] **앱 exe 직접 실행** → 감시로 넘어가 앱이 감시 아래에서 뜬다(앱 옆에 감시 exe가 있을 때).
- [ ] **바로가기 두 번 실행** → 앱이 하나만 뜨고 기존 창이 앞으로 온다.
- [ ] **감시만 끝낸 상태에서 앱만 떠 있을 때 감시를 띄우면** 그 앱을 넘겨받는다(새로 띄우지 않는다).
- [ ] **감시를 하나 더 실행하면** 바로 끝난다.
- [ ] **ASIO 장치 뽑기** → 오디오 멈춤으로 인한 재실행이 연속 3번 뒤 멈춘다(그 뒤로는 기록만 한다). 장치를 다시 꽂아 콜백이 돌면 횟수가 초기화된다. `supervisor.log`로 확인한다.
- [ ] **공연 중 새 버전 설치(업그레이드).** 공연이 재생 중인 상태(감시와 앱이 떠 있음)에서 새 `AtmosMixerPro_Setup.exe`를 실행한다.
  - installer(`PrepareToInstall`)가 **감시를 먼저, 앱을 그다음에** 끝낸다. 감시가 먼저 꺼지지 않으면 앱을 끝낼 때 감시가 앱을 다시 띄워 파일이 잠긴다.
  - 설치가 파일 잠금 오류 없이 끝나고, 설치 도중과 끝난 직후에 앱이 저절로 다시 뜨지 않는다. 설치 마지막 화면에 실행 체크 항목은 없다(2026-10-24) — 바탕 화면·시작 메뉴 바로가기로 시작한다.
  - 업그레이드 뒤 설치 폴더의 `data\flutter_assets\assets\models`에 `listener_bust_white.obj`·`room_frame.glb`·`speaker_cube.glb`만 있다(설치 파일이 예전 파일을 이름으로 지운다, 2026-10-24). 예전 흉상 파일(`listener_bust.obj`, `listener_head.obj` 등)이 남아 있으면 안 된다.
  - 설치 후 바로가기·로그인 자동 실행(작업 스케줄러 작업 "The Awesome Autostart", 2026-10-23부터 Run 키 대신)이 새 감시 exe를 가리키고, 새 버전이 뜬다. 작업은 로그인한 사용자 계정·로그온 10초 뒤·시간 제한 없음이고, 옛 Run 값(AtmosMixerPro)은 업그레이드 때 지워진다.
  - 작업 대상은 UAC를 승인한 계정이 아니라 지금 Windows 세션에 로그인한 사용자다(2026-10-24). 설치 로그(`%TEMP%\Setup Log *.txt`)의 `registered: session user … (SID), setup account …; task … (SID), trigger …, Limited, Interactive` 줄에서 세션 사용자·작업 계정의 SID가 같고 Limited·Interactive인지 본다. 다른 관리자 계정으로 승인했다면 setup account만 그 계정이고 작업은 로그인한 사용자여야 한다. 로그인 뒤 작업 관리자 세부 정보에서 `atmos_supervisor.exe`·`atmos_mixer_pro.exe`의 "관리자 권한 상승"이 "아니요"인지 본다.
  - 앱이 뜬 뒤 작업 표시줄 버튼을 오른쪽 클릭하면 이름이 The Awesome이고(옛 `atmos_mixer_pro`가 아니다), 작업 관리자에도 The Awesome으로 보인다. 작업 표시줄에 고정하면 시작 메뉴의 The Awesome 바로가기(감시)가 고정된다.
  - 제거(`UninstallRun`)도 같은 순서(감시 먼저, 앱 그다음)로 끝나는지 확인한다.
  - 확인은 작업 관리자에서 `atmos_supervisor.exe`와 `atmos_mixer_pro.exe`의 종료 순서, `supervisor.log`의 기록으로 한다.
- [ ] **점검 중 주의.** 대기 중인 앱이 충돌하면 `--auto-relaunched`로 다시 뜨고, 재생 중이던 게 없었으면 첫 방 테마로 시작한다. 점검할 때 환경설정 스위치만 꺼서는 이를 막지 못한다. 점검 전에 감시를 끝낸다.

## 3. 오디오: 장치, ASIO, 메모리

macOS에서 실측한 값(Scarlett 6i6 12ch, 48kHz)과 비교한다. Windows에서 같은 결과가 나와야 한다.

- [ ] **장치 목록.** ASIO와 WASAPI 장치가 `[ASIO]`, `[WASAPI]` 접두어로 보이고, 현장에 연결한 인터페이스가 제품과 상관없이 보인다. 고르고 저장하면 엔진이 그 장치를 열고, 그 장치의 출력 채널 수와 이름이 채널 매핑 화면에 나온다(HANDOFF 확정된 결정 "오디오 인터페이스"). FL Studio ASIO·Generic Low Latency ASIO 같은 가상 드라이버도 목록에 보이지만 현장에서는 고르지 않는다.
- [ ] **재생과 정지.** 트랙 재생·정지·전체 정지가 되고 정지 뒤 소리가 남지 않는다. 서브 라우팅(80Hz·LR24)이 macOS와 같은 방식으로 나뉜다.
- [ ] **ASIO 재시작 복원.** 재생 중 ASIO 리셋 요청(`kAsioResetRequest`)이나 장치 뽑았다 꽂기에서, 엔진이 다시 뜨고 재생이 멈춘 위치부터 이어진다(옛 엔진을 닫고 새 엔진을 여는 순서가 ASIO 단일 클라이언트와 맞아야 한다). 재개 대기 중은 디지털 무음이다.
- [ ] **비상 전환과 복귀(HANDOFF ⚠️ 15).** 재생 중 ASIO 인터페이스 USB를 30초 넘게 뽑는다 → WASAPI 기본 장치로 비상 전환하고 출력이 −40dB로 줄어든다(앱 로그 "비상 전환: …"). 다시 꽂는다 → 몇 초 안에 ASIO 장치를 이름으로 다시 열어 원래 크기로 돌아온다(앱 로그 "비상 전환 해제 시도…", "비상 전환 해제…"). ASIO 목록은 설치된 드라이버 기준이라 뽑혀 있어도 장치가 목록에 남을 수 있다. 그러면 비상 엔진이 다시 시작할 때마다 ASIO 열기를 먼저 시도하다 실패해 바로 다시 비상 전환한다 — 이 시도가 빨리 끝나는지(무음이 길어지지 않는지), 반복되지 않는지 본다. Windows에서는 ASIO 드라이버가 목록에 있으면 30초를 기다리지 않고 바로 열기 실패로 비상 전환될 수 있다(그대로 기록한다).
- [ ] **장치 목록 검사의 안전.** 앱이 ASIO로 재생하는 동안 3초마다 하는 장치 목록 검사가 소리를 끊거나 엔진을 재시작시키지 않는지, 30분 이상 재생하며 앱 로그의 재시작·오류 기록으로 본다.
- [ ] **버퍼와 지연.** ASIO 드라이버가 정하는 버퍼 크기가 설정(`buffer_size` 512)과 다를 수 있다. 스피커 간 지연(시간 정렬)이 macOS와 같게 들리는지 확인한다.
- [ ] **샘플레이트.** 장치 기본 샘플레이트(44.1/48/96kHz)와 파일 샘플레이트가 다를 때(리샘플링) 재생·재개가 정상이다.
- [ ] **채널 이름.** ASIO 장치는 엔진이 연 드라이버가 준 이름이 보인다(HANDOFF 9번, 2026-10-11). 스피커 배치·스피커 속성·FX는 `Ch-1 (Analog 1)`, 메인 트랙 출력·환경설정 트랙 매핑은 `Mono (Ch-1) · Analog 1`, `Stereo (Ch-1/Ch-2) · Analog 1/2`, Output Config 창은 이름 칸의 흐린 글씨다(모든 채널에 같은 RME 장치 번호 "(1)"은 뗀다). 앱 로그의 "ASIO 출력 채널 이름 N/N개" 줄로 드라이버가 준 이름을 본다. WASAPI와 엔진이 열지 않은 장치는 이름 없이 `Ch-N`만 보인다. 확장 장비(ADAT·MADI·Dante 등)를 바꾸거나 드라이버 설정에서 채널 수가 바뀌면 앱을 다시 시작한다(이름은 엔진이 장치를 열 때 읽는다). 현장 장비에서 드라이버 내부 가상 채널(예: DAW 리턴)이 물리 채널처럼 보이지 않는지 확인한다.
- [ ] **관리자 권한과 메모리.** 앱이 관리자로 실행되면 MMCSS 승격과 작업 집합 500MB~2GB 고정을 시도하고(`apply_windows_admin_optimizations`), 일반 계정이면 표준 스케줄링이다. 두 경우 모두 큰 WAV 캐시(예: 10분 4채널 약 470MB)와 장시간 재생에서 소리가 끊기지 않는지, 작업 관리자의 작업 집합이 2GB에 가까워지지 않는지 본다.
- [ ] **현장 샘플레이트 48kHz(HANDOFF 확정된 결정, 2026-10-22).** 앱을 끈 상태에서 인터페이스 설정 앱으로 48kHz를 맞추고(다른 장비와 클럭을 맞추는 현장이면 그 장비 기준), 앱을 켜서 앱 로그의 "오디오 엔진: … Hz"가 그 값인지 본다. 인터페이스를 다시 연결하거나 전원을 껐다 켠 뒤에도 같은 값인지 본다(2026-10-21 이 PC의 RME는 다시 꽂은 뒤 44.1kHz로 돌아왔다). 앱이 재생하는 동안에는 설정 앱에서 바꾸지 못할 수 있다.
- [ ] **리미터 Autoguard를 뺀 뒤 다시 듣기(HANDOFF 확정된 결정, 2026-10-24).** 채널마다 큰 소리를 몰래 낮추던 기능을 뺐으므로, 그동안 낮아지던 채널(특히 서브·LFE +10dB를 쓰는 방)이 커질 수 있다. 평소 음량으로 공연 전체를 듣고 방·트랙 볼륨을 다시 맞춘다. 스피커 보호는 피크 리미터가 그대로 한다.

## 4. 장시간 (무인 운영)

- [ ] **Release 빌드로 12시간 이상 연속 재생.** 메모리, 드롭아웃·무음, 로그 크기, 감시의 재실행 횟수를 기록한다. 메모리 비교 기준: macOS 릴리스 앱은 재생 중 분당 0.09~0.3MB(12시간 약 65~200MB) 늘었다(처음의 분당 2.2MB는 디버그 빌드·테스트 하네스 측정이었다, HANDOFF 남은 일 6). 12시간에 수백 MB 넘게 늘면 Flutter DevTools(프로필 모드)로 화면 그리기 쪽을 본다.
- [ ] **절전 방지.** 관리자 명령 프롬프트에서 `powercfg /requests`를 실행해 SYSTEM 항목에 앱이 보인다(걸린 것). 사람이 직접 절전시킨 뒤 깨우면 멀쩡한 앱을 죽이지 않는다(감시가 확인 간격 5초 초과를 절전으로 본다).

## 5. 네트워크 (OSC)

- [ ] **방화벽 허용 창.** OSC가 `0.0.0.0`(UDP)으로 열린다. 설치 파일이 규칙 2개(`The Awesome OSC`: 개인·도메인 네트워크 전체 허용, `The Awesome OSC (public, local subnet)`: 공용 네트워크는 같은 서브넷만. 2026-10-22 이름 변경 전 설치본은 `Atmos Mixer Pro OSC`…)를 넣으므로 설치본 첫 실행에서 허용 창이 뜨지 않아야 한다(2026-10-08 결정). "고급 보안이 포함된 Windows Defender 방화벽"의 인바운드 규칙에서 두 규칙을 확인하고, 제거하면 사라지는지 본다. 업그레이드 뒤에도 규칙은 이 두 개뿐이고 옛 이름(`Atmos Mixer Pro OSC`)이 없어야 한다(설치 파일이 이 exe의 규칙과 옛 이름 규칙을 지우고 다시 넣는다). 2026-10-23 개발 PC에서는 보안 프로그램이 설치를 가로채 지우기가 실패하고 규칙이 쌓였으므로(0절 보안 프로그램 항목), 이 확인은 예외를 넣은 PC나 Windows 방화벽만 쓰는 PC에서 한다. 개발 빌드(Debug, CI 폴더)는 exe 경로가 달라 창이 뜬다.
- [ ] **OSC 네트워크 구성(사용자 확인 2026-10-08).** OSC 장비는 현장 PC와 같은 LAN·같은 서브넷에 둔다. 현장 PC 고정 IP, 네트워크 종류 "개인"(`Get-NetConnectionProfile`로 확인)을 확인하고, 현장 PC IP·OSC 장비 IP·포트를 결과 기록에 적는다. 서브넷이 다른 구성이면 라우터가 UDP를 넘기는지 따로 본다.
- [ ] **OSC 수신.** 외부에서 설정된 포트로 `/theme/start`, 트랙 재생·정지, 방 비우기를 보내 동작한다. 같은 주소가 겹치면 마지막 것만 기억한다(HANDOFF 남은 일 5번).

## 6. 로그

- [ ] **로그 회전.** 앱 로그와 감시 기록이 10MB를 넘으면 밀리고 파일이 최대 5개(앱 로그 기준)만 남는다. **메모장 등으로 로그 파일을 열어 둔 상태**에서도 회전 실패로 줄이 사라지지 않는다(회전에 실패하면 지금 파일에 계속 쓴다).
- [ ] **로그 내보내기.** 메뉴 "Export Log"가 바탕화면 폴더에 저장한다. 바탕화면이 OneDrive 아래로 옮겨진 PC와 그렇지 않은 PC 모두, 한글 폴더명("바탕 화면")이 있는 경우도 확인한다. 폴더를 찾지 못하면 폴더를 고르는 창이 뜬다. 내보낸 폴더에 `supervisor.log`(밀린 것 포함)도 있다.

## 7. 3D 방 뷰어 (필수)

사용자 결정으로 Windows에서도 반드시 동작해야 한다. `webview_flutter`는 Android·iOS·macOS만 지원해서 Windows용 구현이 따로 필요하고, 구현 전에는 이 절이 실패하는 것이 정상이다. 구현 방식은 Windows PC에서 작은 실험으로 정한다(후보: `webview_windows` 0.4.0, `flutter_inappwebview` 6.1.5).

- [ ] 스피커 배치 화면에서 3D 방이 표시된다(로딩 스피너가 계속 돌지 않는다).
- [ ] 청취자 자리에 흰 흉상(`listener_bust_white.obj`, 2026-10-24 교체)이 받침대 위에 서 있고, 귀가 방의 귀 높이(기본 1.2m)에 오며 얼굴이 정면(앞 벽) 쪽을 본다. 흉상 대신 받침대만 보이면 모델을 읽지 못한 것이다(3D 화면 콘솔의 "3D 모델 로드 실패").
- [ ] WebGL이 매끄럽게 돈다(체감 끊김 없음, 가능하면 프레임 속도 측정).
- [ ] 스피커를 3D에서 탭하면 선택되고 인스펙터 패널이 열린다(`SPEAKER_SELECTED`).
- [ ] 스피커를 드래그하면 위치가 Dart로 전달되고 FX가 따라간다(`SPEAKER_DRAGGING`, `SPEAKER_MOVED`). 헤드폰 미리듣기·자동 EQ가 macOS와 같은 값으로 갱신된다.
- [ ] 카메라 시점 전환 버튼이 동작한다.
- [ ] WebView2 런타임이 없는 PC에서 앱이 죽지 않고 안내나 대체 화면을 보여준다.
- [ ] 3D가 실패해도 감시의 첫 하트비트는 정상으로 간다(하트비트는 `AtmosMixerProApp.initState`의 타이머라 3D와 무관하다).

## 8. 메뉴와 화면

- [ ] **메뉴 항목 동일성.** macOS는 네이티브 메뉴(`PlatformMenuBar`), Windows는 Material 메뉴로 따로 구현돼 있다. macOS 메뉴의 File(Load Project, Save Project, Export Log), View(Toggle Exhibition Mode, OSC Packet Monitor), Settings·Preferences에 해당하는 항목을 Windows에서 모두 찾을 수 있다. (Windows 메뉴 코드에서 Settings·Preferences가 이 구간에는 보이지 않았다. 화면 다른 곳에 있는지 확인한다.)
- [ ] 프로젝트 저장·불러오기가 된다. 파일 선택 창이 Windows에서 정상이다.
- [ ] 창 크기·최소 크기(800×600)·타이틀바가 정상이다.
- [ ] **리샘플링 배지(2026-10-24).** 장치와 같은 샘플레이트 음원만 재생하거나 아무것도 재생하지 않으면 `DIRECT: 48kHz`, 다른 음원(예: 44.1kHz)을 재생하면 `HQ Sinc: 44.1kHz ➔ 48kHz (트랙 n개)`로 바뀌고, 멈추면 돌아온다. 인터페이스 샘플레이트가 다르면(또는 비상 전환으로 기본 장치가 되면) 장치 값도 그 값으로 보인다.
- [ ] **리미터 미터(2026-10-24).** 큰 음원을 틀어 리미터가 걸리면 `TRUE-PEAK LIMITER ISP -x.x dB`가 공연 중 계속 움직이고, 작아지면 0.0으로 돌아온다(예전에는 재생·정지 때만 바뀌었다).
- [ ] **ASIO 로고와 상표 고지(Windows만).** Help → Third-party Notices 맨 아래에 ASIO 로고(변형 없이 180px)와 문구 2줄("ASIO is a registered trademark of Steinberg Media Technologies GmbH."와 계약서 3조 1항 k 문구)이 보인다. macOS 판에는 이 칸이 없다.

## 9. 프로젝트 파일 이식성 (설계 PC → 현장 PC)

사용자 결정(2026-10-05): 오디오와 도면을 `.atmos` 파일과 같은 폴더(하위 폴더 가능)에 담아 옮긴다. 프로젝트를 열 때 저장된 경로에 파일이 없으면 `.atmos` 폴더에서 같은 파일 이름으로 다시 연결한다(구현됨, PR #10으로 병합, Windows 확인 전).

- [ ] **준비.** macOS에서 프로젝트를 저장하고, `.atmos`와 오디오·도면을 같은 폴더(하위 폴더 가능)에 담아 USB로 Windows PC에 옮긴다. 2026-10-10부터는 **File > Export Project**가 정한 이름의 폴더에 `project.atmos`·`audio\`·`drawing\`을 한 번에 모아 준다.
- [ ] **그대로 열기.** Windows에서 메뉴 "Load Project"로 연다(macOS 네이티브 메뉴와 Windows Material 메뉴 모두 대시보드의 같은 `_loadProject`를 부르므로 Windows 메뉴에서 연다). 못 찾은 파일 대화상자 없이 열리고, 트랙이 재생되고, 도면이 보인다.
- [ ] **일부를 다른 폴더에 둔 경우.** 오디오 일부를 `.atmos` 폴더 밖에 두고 열면 "파일 N개를 찾지 못했습니다" 대화상자가 뜬다. "폴더 고르기"로 그 폴더를 고르면 같은 방법으로 찾아 연결된다. "그대로 열기"를 누르면 그대로 열린다. (대화상자의 버튼은 사람이 실제로 눌러 봐야 한다. 자동 확인이 안 됐다.)
- [ ] **끝까지 없는 파일.** 연 뒤 못 찾은 파일 목록이 나오고 앱 로그에도 남는다. 그 트랙은 원래 경로 그대로이고, 재생하면 어떤 증상이 나오는지(오류 표시, 무음, 로그만 남김)를 기록한다.
- [ ] **연결 유지.** 앱을 다시 켜도 연결이 유지된다. 다시 연결한 경로는 이 PC의 `config.json`과 도면 설정에 저장된다.
- [ ] **내보낸 뒤에도 지금 프로젝트는 원래 음원.** File > Export Project로 내보내기 전후로 이 PC 앱 데이터의 `config.json`(`%APPDATA%\com.example\atmos_mixer_pro\`) 체크섬이 같고, 트랙 경로가 원래 음원 그대로다. 내보낸 폴더의 `project.atmos`는 그 폴더 `audio\` 복사본을 가리킨다. 앱을 다시 켜도 원래 음원으로 재생된다. (2026-10-10까지는 내보낸 직후 지금 프로젝트와 `config.json`이 복사본 경로로 바뀌었다. 2026-10-11에 고침, HANDOFF 14.)
- [ ] **이름 규칙.** 파일 이름 대소문자가 달라도 연결된다. `/`와 `\`가 섞인 저장 경로도 인식한다. 같은 이름이 여러 폴더에 있으면 원래 경로와 상위 폴더 이름이 가장 많이 겹치는 파일이 연결된다(같으면 얕은 쪽). 숨김 파일·폴더는 무시된다. 한글·공백이 든 경로에서도 열린다(이 항목은 구현 설명에 없는 추가 확인이다).
- [ ] **도면 이미지.** 도면도 같은 방식으로 다시 연결되어 보인다.
- [ ] 스피커 배치, 방 설계, 채널 FX(EQ·게인·딜레이·위상)가 옮겨지고 값이 같다.

## 10. 자동 테스트를 Windows에서 돌려 보기 (개발 PC)

- [ ] **통합 테스트.** `flutter test integration_test/app_flow_test.dart -d windows`를 시도한다. 부팅, 재생·정지, 스피커 배치·인스펙터, 스피커 이동·FX, 서브 라우팅, 재시작 복원, 테마 시작 단계 중 어느 단계가 실패하는지 적는다. 실패하는 단계가 macOS와 동일하지 않은 지점이다. 이 테스트는 기본 출력 장치(`device_name: null`)를 쓰는데 Windows에서는 WASAPI 기본 장치가 되고, 3D에 의존하는 단계는 3D 구현 전에는 실패할 가능성이 크다.
- [ ] **Rust 테스트.** `rust/`에서 `cargo test`가 Windows에서 컴파일되고 통과하는지 본다. 유닉스·macOS 전용 시험은 Windows에서 빠진다(`test_analysis_thread_idle_cpu.rs`는 `#![cfg(unix)]`, `diag_engine_restart_leak.rs`·`diag_playback_memory.rs`는 `#![cfg(target_os = "macos")]`, HANDOFF 12번). 장치가 필요 없는 DSP 테스트가 macOS와 같은 수치로 통과하는지 본다.
- [ ] **로더.** Windows 앱은 실행 파일 옆의 `rust_lib_atmos_mixer_pro.dll`을 직접 연다(`lib/core/utils/rust_library.dart`, HANDOFF 13번). 개발 PC에서 프로젝트 폴더로 `flutter run -d windows`했을 때 `rust/target/release`의 옛 dll이 아니라 방금 빌드한 dll이 실리는지 본다. 앱이 떠 있는 동안 PowerShell에서 `(Get-Process atmos_mixer_pro).Modules | Where-Object ModuleName -eq 'rust_lib_atmos_mixer_pro.dll' | Select-Object FileName`이 `build\windows\x64\runner\Debug\`(또는 `Release\`) 아래 경로를 보여야 한다.
