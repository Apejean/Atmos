# 충돌·멈춤 후 자동 재실행 — 설계

- 날짜: 2026-10-05
- 배경: 현장(전시 운영) PC는 Windows이고 무인으로 돈다. 지금은 앱이 죽거나 멈추면 누가 알아챌 때까지 전시가 조용하다. HANDOFF "남은 일" 3번(Windows 기준 우선순위 3번)이다.

## 0. 사용자 결정(2026-10-05)

1. 다시 띄우는 경우는 **충돌과 멈춤 때만**이다. 운영자가 일부러 닫으면 그대로 닫힌 채로 둔다.
2. **감시가 다시 띄운 경우**에는 공연을 자동으로 이어 간다. 사람이 바로가기로 켤 때는 지금처럼 대기한다.
3. 감시는 **별도 Rust 감시 프로그램**으로 만든다.
4. 한계 보완을 모두 넣는다.
   - 중복 실행 막기와 감시로 넘기기
   - 떠 있는 앱도 넘겨받기
   - 기존 창 앞으로
   - 재생 위치까지 이어 틀기
   - 오디오 상태를 신호에 넣기
   - 재생 중 무음 경고
   - macOS 끝까지 확인 + Windows 현장 점검표
5. **재부팅·정전 뒤 로그인 자동 실행**은 환경설정 "로그인할 때 공연 자동 시작"으로 정한다(기본 켜짐).
6. CI에 PR 트리거를 추가해 PR마다 Windows 빌드를 자동으로 돌린다.

## 1. 지금 구조

- installer(`windows/installer.iss`)가 로그인 때 앱을 띄운다(HKCU `...\Run`의 `AtmosMixerPro`). 바로가기와 설치 직후 실행도 앱을 직접 띄운다.
- 창을 닫으면 `main.dart`의 `onWindowClose`가 엔진을 멈추고 창을 없앤다. Windows 러너는 그 뒤 `EXIT_SUCCESS`(0)를 돌려준다.
- 충돌을 다루는 코드, 앱 중복 실행을 막는 코드가 없다.
- 오디오 엔진 안의 멈춤(콜백 공백)은 엔진 워치독과 재시작 복원이 이미 다룬다. 이 설계는 **앱 프로세스 전체**가 죽거나 멈춘 경우를 다룬다.
  - 마지막 오디오 콜백 시각: `GLOBAL_STATE.watchdog_last_callback`(밀리초)
  - 엔진이 켜져 있는지: `ENGINE_ACTIVE`
  - 재생 위치: 커서 표(`CURSOR_TABLE`)와 `api_get_playback_positions`
  - 위치부터 재생: `play_track_from(room, track, seconds)`

## 2. 왜 이 방식인가

| 방식 | 판단 |
|---|---|
| Windows 기본 기능(`RegisterApplicationRestart`) | 앱이 60초 이상 돈 뒤에만 동작하고 오류 보고 대화상자 설정에 영향을 받는다. "응답 없음" 멈춤은 누군가 창을 눌러야 대화상자가 떠서 무인 상태에서는 잡지 못한다. **제외** |
| 작업 스케줄러 "실패 시 다시 시작" | 앱 충돌 때 실제로 다시 띄우는지 확실하지 않고 멈춤도 못 잡는다. **제외** |
| 앱 실행 파일 안(C++ 러너 `--supervise`) | 추가 exe가 없지만 이 Mac에서 테스트할 수 없다. **제외** |
| **별도 감시 프로그램(Rust)** | 감시 로직을 macOS에서 테스트할 수 있다. **채택** |

보완 전 한계 목록에서 이 방식 때문에 생긴 것은 "감시 없이 떠 있던 앱은 감시를 못 받음" 하나뿐이었다. 4.2·5절의 넘겨받기로 없앤다. 나머지 한계(창 앞으로, 이어 틀기 범위, 재부팅 정책, 의도한 소리)는 어느 방식이든 같아서 방식과 상관없이 보완한다.

## 3. 원칙: 종료 코드에 기대지 않는다

- 감시는 앱의 **종료 코드가 아니라 앱이 남기는 신호**로 판단한다(4.2).
  - 그래서 자기가 띄우지 않은 앱도 감시할 수 있다.
  - 창을 닫다가 앱이 죽어 종료 코드가 0이 아니어도, 운영자가 닫은 것으로 정확히 안다.
- 종료 코드는 "중복 실행이라 끝남"(3) 같은 보조 정보로만 쓴다.

## 4. 구성요소

### 4.1 감시 프로그램 `atmos_supervisor`

- 위치: `atmos_mixer_pro/supervisor/`. 작은 Rust 크레이트(바이너리 + 라이브러리)다.
  - 의존성은 프로세스 핸들용 `windows-sys`(Windows)와 `libc`(macOS)뿐이다.
  - 오디오 라이브러리(`rust/`)와 섞지 않아 빌드가 빠르고, ASIO SDK 같은 Windows 빌드 조건에 묶이지 않는다.
- 띄우는 대상: 기본은 감시 프로그램과 같은 폴더의 앱(Windows는 `atmos_mixer_pro.exe`). `--app <경로>`로 바꿀 수 있다(macOS 확인·테스트용).
- 앱에 넘기는 인자
  - 항상 `--supervised`를 붙인다(4.3).
  - 다시 띄울 때는 `--auto-relaunched`를 붙인다(4.4).
  - 감시가 `--logon`으로 실행됐으면 첫 실행에 `--logon`을 넘긴다(4.4).
- 판단 시간은 인자로 바꿀 수 있다(`--hang-secs`, `--first-heartbeat-secs`, `--audio-stall-secs`). 기본값은 5.1의 표다. 테스트와 macOS 확인에서는 짧게 준다.
- 공유 파일은 모두 앱 로그 폴더(`core::log_file::log_dir()`, 임시 폴더 아래 `atmos_mixer_pro_logs`)에 둔다. 감시와 앱이 같은 사용자로 돌므로 같은 폴더를 본다.

### 4.2 앱이 남기는 신호

| 파일 | 누가·언제 | 내용 |
|---|---|---|
| `app.lock` | 앱이 시작 관문에서 `File::try_lock`으로 잡고 끝날 때까지 쥔다 | 중복 실행 막기용 잠금. Windows 잠금은 다른 프로세스가 내용을 못 읽으므로 PID는 따로 쓴다 |
| `app.pid` | 앱이 잠금을 잡은 직후 쓴다 | 앱 PID |
| `heartbeat` | Dart UI의 `Timer.periodic`(2초)이 Rust API `api_heartbeat()`를 부르면 Rust가 쓴다 | `pid=`, `ui_ms=`(지금 시각), `audio_cb_ms=`(`watchdog_last_callback`), `engine_active=`(0/1), `silent_warnings=`(4.5). 감시가 의존성 없이 읽을 수 있는 `키=값` 줄 |
| `clean_exit` | 운영자가 창을 닫을 때(`onWindowClose`) 엔진을 멈추기 전에 Rust API `api_mark_clean_exit()`가 쓴다 | `pid=`(닫는 앱의 PID) |

- 모든 쓰기는 임시 파일에 쓰고 이름을 바꾼다(반쯤 쓴 파일을 감시가 읽지 않게).
- 하트비트는 Dart UI가 얼어도, Rust 쪽이 막혀 FRB 호출이 안 끝나도 끊긴다. 둘 다 잡는다.
- 오디오 스레드는 건드리지 않는다(DSP 3법칙). 콜백 시각은 이미 있는 원자 값을 읽기만 한다.

### 4.3 시작 관문

Dart `main`은 화면을 띄우기 전에 Rust API `api_startup_gate(args)`를 부르고 결과대로 한다. 판단은 Rust에서 해서 테스트할 수 있다.

1. **감시로 넘기기.** 아래가 모두 맞으면 감시 프로그램을 띄우고 앱은 바로 끝낸다(종료 코드 0). 감시가 앱을 다시 띄운다.
   - 인자에 `--supervised`가 없다(감시 없이 직접 실행됨).
   - 앱 옆에 감시 exe가 있다(개발 빌드·macOS에는 없어 넘기지 않는다).
   - 감시가 돌고 있지 않다(감시 잠금이 비어 있음).
2. **중복 실행 막기.** `app.lock`을 못 잡으면 다른 앱이 이미 떠 있다.
   - 그 앱(`app.pid`)의 창을 앞으로 가져온다(Windows: 그 PID의 최상위 창을 찾아 `ShowWindow`·`SetForegroundWindow`).
   - 그리고 끝낸다(종료 코드 3, "중복 실행").
3. 그 밖에는 `app.lock`을 잡고 `app.pid`를 쓴 뒤 진행한다. 남아 있을 수 있는 이전 `clean_exit`은 지운다.

창은 `window_manager`의 `waitUntilReadyToShow` 뒤에 보이므로, 관문에서 끝나면 창이 깜빡이지 않는다.

### 4.4 공연 이어 가기

- **상태 저장.** Rust의 전용 스레드가 5초마다 앱 지원 폴더의 `show_state.json`에 저장한다(임시 파일에 쓰고 이름 바꾸기).
  - 저장 시각
  - 활성 방
  - 재생 중인 트랙마다 방 ID, 트랙 ID, 재생 위치(초). 루프·단발 모두.
- **이어 가기 `api_resume_show()`.** 앱 시작 절차(설정을 Rust에 적용하고 엔진이 준비됨, `EngineReady`)가 끝난 뒤 한 번 부른다.
  - 저장 파일이 있고, 10분 안에 저장됐고, 저장된 트랙 중 하나라도 지금 설정에 남아 있으면 이어 간다.
    - 그 방을 활성으로 하고, 남아 있는 트랙마다 `play_track_from(방, 트랙, 위치)`로 멈춘 위치부터 다시 튼다.
    - 엔진 재시작 복원(R2)처럼 꺼져 있던 시간만큼 앞으로 건너뛰지 않는다. 루프 위치는 한 바퀴 안으로 접힌 값이다.
  - 그렇지 않으면(파일 없음, 10분 지남, 남은 트랙 없음, 재생 중이던 게 없었음) `api_theme_start()`로 첫 방 테마를 시작한다.
  - 어떤 길로 갔는지와 이유를 앱 로그에 남긴다.
- **`api_theme_start()`** 는 OSC 테마 시작과 같은 동작이다: 전체 정지 → 설정의 첫 방을 활성으로 → 그 방 루프 재생. OSC `ThemeStart`도 이 함수를 부르게 바꾼다.
- **언제 이어 가나**
  - `--auto-relaunched`(감시가 충돌·멈춤 뒤 다시 띄움): 항상 이어 간다.
  - `--logon`(로그인 자동 실행): 환경설정 "로그인할 때 공연 자동 시작"(기본 켜짐)이 켜져 있을 때만 이어 간다. 정전처럼 오래 꺼져 있었으면 10분 규칙에 따라 첫 방 테마로 시작한다.
  - 둘 다 없음(사람이 바로가기로 켬): 지금처럼 대기한다.
- 환경설정 값은 Dart(SharedPreferences, 기본 켜짐)에 두고 환경설정 창에 켜고 끄는 항목을 둔다. 점검하러 재부팅할 때 끈다.

### 4.5 재생 중 무음 경고

- 4.4의 저장 스레드가 같은 주기로 본다. 재생 목록에 루프 트랙이 있고, All Mute가 꺼져 있고(`GLOBAL_STATE.master_mute`), 모든 출력 채널 피크(`GLOBAL_STATE.vu_levels`)가 60초 넘게 정확히 0이면 앱 로그에 경고를 남긴다.
- 같은 상태가 이어지면 10분마다 다시 남긴다. 소리가 나면 초기화한다.
- 재실행은 하지 않는다. 라우팅·장치 문제는 다시 띄워도 해결되지 않는 경우가 많다. 경고 횟수는 하트비트(`silent_warnings=`)에 넣어 감시 기록에도 남긴다.

## 5. 감시 동작

```
시작
 ├─ 감시 잠금(supervisor.lock)을 File::try_lock으로 잡는다. 이미 잡혀 있으면(감시가 이미 돎) 바로 끝낸다.
 └─ 반복
     ├─ 대상 정하기
     │   ├─ app.pid의 프로세스가 살아 있으면 → 그 앱을 넘겨받는다(프로세스 핸들을 열어 둔다. Windows는 핸들이라 PID가 재사용돼도 안전)
     │   └─ 없으면 → heartbeat와 clean_exit을 지우고 앱을 띄운다(--supervised, 필요하면 --auto-relaunched·--logon)
     ├─ 1초마다 본다
     │   ├─ 앱 프로세스가 끝났다
     │   │   ├─ clean_exit의 pid가 이 앱이다 → 운영자가 닫았다. 감시도 끝낸다.
     │   │   ├─ 종료 코드 3(중복 실행) → 다른 앱이 떠 있다. 바로 다시 "대상 정하기"(넘겨받기)
     │   │   └─ 그 밖(충돌) → 기록하고 대기 후 재실행(--auto-relaunched)
     │   ├─ 하트비트가 아직 한 번도 안 왔고 시작한 지 90초가 지났다 → 멈춤(시작 중 멈춤)
     │   ├─ ui_ms가 마지막으로 바뀐 지 30초가 지났다 → 멈춤
     │   └─ engine_active=1인데 audio_cb_ms가 마지막으로 바뀐 지 120초가 지났다 → 오디오 멈춤(5.3)
     │       └─ 앱을 강제 종료하고 기록한 뒤 대기 후 재실행(--auto-relaunched)
     └─ 대기 시간: 2초에서 시작해 실패할 때마다 두 배, 최대 60초. 앱이 5분 이상 잘 돌았으면 2초로 되돌린다.
```

### 5.1 판단 기준(수치)

| 항목 | 값 | 이유 |
|---|---|---|
| 하트비트 간격 | 2초 | 파일 쓰기 부담이 없고 멈춤 판단보다 충분히 촘촘하다 |
| 멈춤 판단 | `ui_ms`가 30초 동안 안 바뀜 | Dart가 무거운 일(재동기화, 3D 로딩)로 잠깐 막혀도 잘못 죽이지 않는다 |
| 첫 하트비트 대기 | 90초 | Flutter 시작과 창 초기화를 넉넉히 기다린다. 하트비트 타이머는 `AtmosMixerProApp.initState`(2초 `Timer.periodic`)에서 시작하므로 엔진 기동이나 3D 웹뷰 로딩과 무관하다. Windows에서 3D가 실패해도 하트비트는 간다. 넘겨받은 앱은 하트비트가 이미 있어야 하므로 30초를 쓴다 |
| 오디오 멈춤 판단 | 엔진이 켜져 있는데 `audio_cb_ms`가 120초 동안 안 바뀜 | 엔진 워치독(1초 공백이면 엔진 재기동)과 재시작 복원이 먼저 일할 시간을 준다 |
| 상태 확인 간격 | 1초 | |
| 재실행 대기 | 2초 → 두 배씩 → 최대 60초, 5분 안정 후 초기화 | 시작하자마자 죽는 경우 장치를 계속 두드리지 않는다 |
| 공연 상태 저장 간격 | 5초 | 이어 갈 때 위치가 최대 5초 앞이다 |
| 이어 가기 유효 시간 | 저장 후 10분 | 오래 꺼져 있던 뒤에는 첫 방부터 시작하는 편이 안전하다 |
| 무음 경고 | 루프 재생 중 60초 완전 무음, 이후 10분마다 | |

### 5.2 시간 판단

- 하트비트의 `ui_ms`·`audio_cb_ms`가 이전에 본 값과 달라지면 "바뀌었다"고 본다. 바뀐 시각은 감시 프로그램의 단조 시계(`Instant`)로 잰다. 파일의 시각 값을 벽시계와 비교하지 않으므로 시계 조정(NTP, 시간대 변경)에 영향받지 않는다.
- 감시 루프 자신의 확인 간격이 5초 넘게 벌어지면(절전에서 깨어남 등) 모든 멈춤 타이머를 다시 잰다. 앱은 절전 방지로 시스템 절전을 막지만, 사람이 직접 절전시키면 깨어난 직후 멀쩡한 앱을 죽이면 안 된다.

### 5.3 오디오 멈춤은 마지막 수단

- 엔진 안의 워치독과 재시작 복원이 먼저 일한다. 감시는 그래도 2분 넘게 콜백이 안 돌 때만 앱 전체를 다시 띄운다.
- 장치를 뽑아 둔 상황이면 다시 띄워도 소용없이 반복만 된다. 그래서 오디오 멈춤으로 **연속 3번** 다시 띄웠는데도 살아나지 않으면, 그 뒤로는 오디오 멈춤으로는 다시 띄우지 않고 기록만 한다. 콜백이 다시 돌면(장치 복구) 횟수를 초기화한다.
- UI 멈춤과 충돌에 대한 재실행은 이와 상관없이 계속한다.

### 5.4 기록

- 감시 프로그램의 기록은 앱 로그 폴더의 `supervisor.log`에 남긴다: 시작, 앱 실행·넘겨받기, 정상 종료, 충돌(종료 코드), 멈춤·오디오 멈춤 판단, 재실행 대기, 오디오 멈춤 재실행 중단, 무음 경고 수 변화.
- 크기 제한은 앱 로그와 같은 규칙(10MB, 최대 5개)이다. 감시 크레이트는 앱 라이브러리를 쓰지 않으므로 같은 회전 규칙을 감시 크레이트 안에 둔다.
- **회전은 줄을 버리지 않는다.** 지금 파일이 크기를 넘으면 먼저 지금 파일을 `<이름>.rotating`으로 옮겨 본다. 옮기지 못하면(Windows에서 다른 프로그램이 기록 파일을 쥐고 있을 때) 아무것도 건드리지 않고 그 줄은 지금 파일에 쓴다. 오래된 파일부터 밀다가 실패하면 줄마다 오래된 기록만 지워지는 예전 방식을 쓰지 않는다. 앱 로그(`core::log_file`)도 같은 규칙으로 고친다.

## 6. 설치·배포

- **installer(`windows/installer.iss`)**
  - 로그인 자동 실행(Run 키)은 `atmos_supervisor.exe --logon`이다.
  - 시작 메뉴·바탕화면 바로가기와 설치 직후 실행은 `atmos_supervisor.exe`다. 바로가기 아이콘은 앱 exe에서 가져온다(`IconFilename`).
  - 감시 exe는 Release 폴더에 함께 들어가므로 `[Files]`의 `Release\*` 복사에 포함된다.
  - 제거 전에 감시와 앱을 끝낸다(installer 제거 단계).
- **CI(`.github/workflows/build_release.yml`)**
  - Windows 빌드에서 `cargo build --release --manifest-path atmos_mixer_pro/supervisor/Cargo.toml`을 돌리고, 결과 exe를 `build/windows/x64/runner/Release/`에 복사한 뒤 압축한다.
  - **PR 트리거**: `pull_request`(main 대상)를 추가해 PR마다 Windows·macOS 빌드가 자동으로 돈다. 릴리스는 지금처럼 태그에서만 한다.
  - 같은 PR에 커밋이 또 올라오면 앞선 실행을 취소한다(`concurrency`).
- macOS 배포에는 감시 프로그램을 넣지 않는다(현장은 Windows).
- 앱 쪽 Windows 코드(창 앞으로)를 위해 `windows` 크레이트에 `Win32_UI_WindowsAndMessaging` 기능을 더한다.

## 7. 테스트

- **감시 크레이트(macOS에서 실행).** 가짜 앱으로 쓸 셸 스크립트를 테스트가 만든다. 스크립트는 앱처럼 `app.pid`·`heartbeat`·`clean_exit`을 쓴다.
  1. `clean_exit`을 남기고 끝남 → 감시가 끝나고 다시 띄우지 않는다. 종료 코드가 1이어도 마찬가지다.
  2. 표시 없이 끝남 → `--auto-relaunched`로 다시 띄운다. 첫 실행과 재실행 모두 `--supervised`가 붙는다.
  3. 하트비트를 쓰다 멈춤 → 멈춤 판단으로 강제 종료하고 다시 띄운다(판단 시간은 짧게 주입).
  4. 하트비트를 한 번도 안 씀 → 첫 하트비트 대기 뒤 강제 종료하고 다시 띄운다.
  5. `engine_active=1`인데 `audio_cb_ms`가 안 바뀜 → 다시 띄운다. 연속 3번 뒤에는 오디오 멈춤으로는 더 띄우지 않는다. 콜백이 돌면 초기화한다.
  6. **넘겨받기**: 감시보다 먼저 떠 있던 가짜 앱(`app.pid`가 살아 있음)을 새로 띄우지 않고 감시한다. 그 앱이 표시 없이 끝나면 다시 띄운다.
  7. 종료 코드 3(중복 실행) → 넘겨받기로 이어진다.
  8. 대기 시간이 두 배씩 늘고 최대에서 멈추며, 안정 시간 뒤 초기화된다(시계를 주입한 순수 함수).
  9. 감시가 이미 돌면 두 번째는 바로 끝난다(잠금 파일). `--logon`은 첫 실행에만 넘어간다.
  10. 하트비트 파일 읽기: 정상 형식, 빠진 키, 반쯤 쓴 내용.
  11. 기록 회전: 크기를 넘으면 밀고 정한 개수만 남긴다. 지금 파일을 옮기지 못하면 밀지 않고 줄은 지금 파일에 남으며 오래된 기록은 그대로다.
- **앱(Rust)**
  - 시작 관문: 직접 실행 + 감시 exe 있음 + 감시 안 돎 → 넘기기. 감시 exe 없음 → 진행. `app.lock`이 잡혀 있음 → 중복(창 앞으로 호출, 종료 코드 3). `--supervised`면 넘기지 않음. 경로·잠금·창 함수는 주입한다.
  - `api_heartbeat()` → 다섯 값이 들어가고, 다시 부르면 `ui_ms`가 바뀐다.
  - `api_mark_clean_exit()` → `clean_exit`에 PID가 들어간다.
  - 공연 상태: 저장 내용(루프·단발, 위치), 이어 가기(멈춘 위치부터 재생 명령이 나감), 첫 방 테마로 돌아가는 경우(파일 없음, 10분 지남, 트랙이 설정에서 사라짐, 재생 중이던 게 없었음).
  - `api_theme_start()` → 첫 방 활성, 그 방 루프만 재생 목록에 오른다. OSC 테마 시작도 같은 결과다(기존 OSC 테스트에 더함).
  - 무음 경고: 루프 재생 중 피크가 60초 0이면 경고, All Mute면 안 함, 소리가 나면 초기화(시계와 피크 주입).
  - 앱 로그 파일: 회전 실패 시 줄을 버리지 않는다(위 5.4 규칙), 내보내기가 `supervisor.log`(밀린 것 포함)도 복사한다.
- **앱(Dart)**
  - 실행 인자와 환경설정에 따른 결정: `--auto-relaunched` → 이어 가기, `--logon` + 설정 켜짐 → 이어 가기, `--logon` + 설정 꺼짐 → 대기, 인자 없음 → 대기.
  - 환경설정 항목 기본값(켜짐).
- **macOS 끝까지 확인(수동 스크립트 `tool/supervisor_e2e_macos.sh`).** 감시 프로그램을 빌드해 macOS 앱을 `--app`으로 띄운다(판단 시간은 짧게). 실제 config로 소리가 난다.
  1. 앱 강제 종료(`kill -9`) → `--auto-relaunched`로 다시 뜨고, 앱 로그에 이어 가기 결과가 남는다.
  2. 앱 일시 정지(`kill -STOP`) → 멈춤 판단 뒤 강제 종료되고 다시 뜬다.
  3. 앱 정상 종료(창 닫기) → 다시 뜨지 않고 감시도 끝난다.
  4. 감시를 하나 더 실행하면 바로 끝난다. 앱을 직접 하나 더 실행하면 바로 끝난다.
  5. 감시를 끝낸 상태에서 앱만 떠 있을 때 감시를 띄우면 그 앱을 넘겨받는다.
- **Windows 현장 점검표(`docs/WINDOWS_FIELD_CHECKLIST.md`).** Windows PC 앞에서 순서대로 따라 하는 확인 목록이다. 전체 항목의 기준은 그 문서다(아래는 이 설계에서 나온 부분이다. 3D 방 뷰어, ASIO, 방화벽 등 Windows 동일 동작 점검 항목은 그 문서에 있다).
  - 설치와 로그인 자동 실행(설정 켜짐: 공연 이어 감 / 꺼짐: 대기)
  - 작업 관리자로 강제 종료 → 다시 뜨고 공연이 멈춘 위치부터 이어짐
  - 리소스 모니터로 일시 정지 → 30초 뒤 다시 뜸
  - 창 정상 닫기 → 다시 뜨지 않음
  - 앱 exe 직접 실행 → 감시로 넘어감
  - 바로가기 두 번 실행 → 하나만 뜨고 기존 창이 앞으로 옴
  - ASIO 장치 뽑기 → 오디오 멈춤 재실행이 3번 뒤 멈춤
  - `powercfg /requests`(절전 방지), 로그 내보내기(OneDrive 바탕화면), installer 버전
  - HANDOFF "Windows 미검증" 항목들

## 8. 알려진 한계(보완 뒤에도 남는 것)

- **Windows 실제 동작**은 PR 자동 빌드와 현장 점검표 확인 전까지 보장하지 못한다. 코드로 없앨 수 없다.
- 이어 갈 때 위치는 최대 5초(저장 간격) 앞일 수 있고, 꺼져 있던 시간만큼 건너뛰지 않는다(엔진 재시작 복원과 같은 원칙).
- 하트비트와 오디오 콜백은 "앱이 응답하고 장치가 돈다"는 뜻이다. "의도한 소리가 난다"는 무음 경고로 알리기만 하고 고치지는 않는다.
- macOS의 넘겨받기는 PID로만 살아 있는지 본다(PID 재사용을 완전히 막지 못함). macOS는 확인용이라 받아들인다. Windows는 프로세스 핸들이라 해당 없다.

## 9. 범위 밖

- Windows 서비스 방식(세션 0이라 GUI·오디오 장치 사용이 맞지 않는다).

- 원격 알림(재실행·무음 경고를 운영자에게 보내기).
