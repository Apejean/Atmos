# 앱 흐름 통합 테스트와 재시작 재생 복원 — 설계 (2026-10-01)

## 1. 목적

실제 앱 전체(Flutter 위젯 → Riverpod → FFI → Rust 엔진 → 오디오 장치)에서 다음 흐름을 자동으로 조작하고 검증한다.

1. 재생/정지
2. 스피커 이동에 따른 채널 FX 반영
3. 서브 라우팅
4. 엔진이 스스로 재시작한 뒤의 복원
5. "테마 시작" 루프

최근 실기 버그(정지해도 소리가 남, FX가 스피커를 안 따라감, 서브로 저역이 안 감)나 이번에 새로 만드는 재시작 복원이 다시 깨지면 이 테스트가 실패해야 한다. 사람이 화면을 조작하며 확인하던 일(HANDOFF "남은 일 2")을 대신한다.

## 2. 확정된 결정

| 결정 | 내용 |
|---|---|
| 접근 방식 | `integration_test`로 실제 앱을 띄우고, 위젯을 조작하고, 앱이 이미 가진 상태와 채널별 출력 피크(VU)로 검증한다 |
| 출력 장치 | 테스트 config.json의 `device_name`은 `null`이다. 엔진은 이때 시스템 기본 출력 장치를 쓴다(`engine.rs` `start`). 장치 이름을 하드코딩하지 않는다. 장치 매칭이 정확한 문자열 일치라 이름이 조금만 달라도("Scarlett 6i6" ≠ "Scarlett 6i6 USB") 30초 뒤 실패하고, 그 장치가 빠져 있어도 실패하기 때문이다 |
| 소리 | 소리가 실제로 난다. 톤은 −30dBFS로 작게 낸다 |
| 범위 | 재생/정지, 스피커 이동 → FX, 서브 라우팅, 재시작 복원, 테마 시작 |
| 재시작 복원 동작 | 엔진이 스스로 재시작하면 재생 중이던 트랙을 **자동으로, 멈췄던 재생 위치(커서)부터** 다시 튼다. 처음부터 다시 틀거나, 정지된 채로 두고 "테마 시작"을 다시 누르게 하지 않는다 |
| 크로스오버 | 80Hz·LR24 유지(기존 확정) |
| 실행 | macOS 실기에서 수동으로 실행한다. CI에 넣지 않는다 |

## 3. 범위 밖

- **Windows 실행.** 이 테스트는 macOS 실기 전용이다. Windows는 크로스 컴파일도 안 되는 상태다(HANDOFF "Windows 미검증").
- **사용자가 직접 엔진을 다시 띄운 경우**(환경설정에서 장치 변경 등)의 재생 복원. 이번 기능은 엔진이 스스로 재시작하는 경로(워치독 콜백 공백, 장치 오류·재설정, 장치 목록 변화)만 다룬다.
- **3D 장면 안의 클릭 판정.** 스피커 캔버스의 3D 방은 Three.js를 WebView로 그리는 화면이라 WidgetTester가 그 안을 누를 수 없다. 테스트는 장면이 노드를 탭했을 때 보내는 메시지를 JS 채널에 그대로 넣는다(5절 2단계). 채널부터 뒤는 전부 실제 코드이고, JS 쪽 클릭 판정은 검증하지 않는다(10절).
- **3D 드래그로 스피커 옮기기.** 스피커는 인스펙터 슬라이더로 옮긴다.
- **실제 음원 청음.** LR24는 선형 필터라 톤 응답으로 모든 신호의 분할 비율이 정해진다.

## 4. 격리

테스트는 사용자의 실제 프로젝트를 읽지도 쓰지도 않는다.

- **앱 지원 폴더.** `PathProviderPlatform.instance`를 가짜로 바꿔 테스트 임시 폴더를 돌려준다. 앱의 `config.json`(`getApplicationSupportDirectory()/config.json`)은 그 폴더에 생긴다.
- **SharedPreferences.** `SharedPreferences.setMockInitialValues({})`로 메모리에만 둔다. 스피커 배치, 튜닝, 베이스 설정, 리버브가 여기에 저장된다.
- **픽스처.** 테스트가 실행 때 임시 폴더에 직접 만든다.
  - 톤 WAV, 48kHz 모노, −30dBFS:
    - 200Hz 2초 루프, 50Hz 2초 루프. 정수 주기라 루프 이음매에 클릭이 없다.
    - 200Hz 20초, 50Hz 20초. 루프가 아니며 재시작 복원 단계에서 쓴다.
  - `config.json`: `device_name: null`, 방 1개(크기 지정). 트랙 4개는 모두 출력 CH2이고, 미리 로드한다(`is_streaming: false`). 2초 톤은 `is_loop: true`, 20초 톤은 `is_loop: false`다. "테마 시작"은 첫 방의 루프 트랙만 틀기 때문에 20초 톤은 끼지 않는다.
- **스피커.** 테스트 중에 스피커 캔버스의 "Add 3D Speaker" 버튼으로 만든다. 첫 번째가 CH1, 두 번째가 CH2다. 이 버튼은 스피커를 추가하면서 그 스피커의 인스펙터를 연다.
- **사전 확인.** 다른 Atmos 앱 인스턴스가 떠 있거나 기본 출력 장치가 2채널 미만이면, 테스트는 조작을 시작하기 전에 이유를 적고 실패한다.

## 5. 시나리오

앱은 한 번만 띄운다. 단계는 앞 단계의 상태 위에서 순서대로 진행한다. 실패 메시지에는 단계 번호를 넣는다.

검증에 쓰는 값은 모두 앱이 이미 가진 것이다.

- 재생 목록: `engineStateProvider.playingTrackIds`
- 튜닝(채널별 게인·딜레이): `tuningStateProvider`
- 출력 피크: 앱의 `vuStreamProvider`. VU 세션은 전역에 하나뿐이라 새 세션을 열지 않고 앱의 스트림을 같이 듣는다.
- 재생 위치: 6절에서 새로 만드는 조회 API

판정 문턱(피크는 선형값을 dBFS로 바꿔 본다):

- 소리 있음: −50dBFS 초과. 톤은 −30dBFS이고, 마스터 헤드룸과 튜닝 게인이 바꿀 수 있는 폭보다 여유를 둔다.
- 무음: −90dBFS 미만. 재생이 없으면 출력은 디지털 무음(0)이다.
- 단계별 레벨 비교 문턱(±1dB 등)은 시험 실행으로 보정한다(12절).

### 0. 부팅

스플래시를 지나 엔진이 준비되고(`apiIsEngineReady`) 대시보드가 뜬다.

### 1. 재생/정지

1. 대시보드 방 카드에서 200Hz 2초 루프의 재생 버튼을 탭한다.
2. 1초 안에 재생 목록에 그 트랙이 들어가고, CH2 피크가 "소리 있음"이 된다.
3. 정지 버튼을 탭한다.
4. 1초 안에 목록에서 빠지고, CH2 피크가 "무음"이 된다.

### 2. 스피커 배치와 인스펙터 열기

1. 대시보드에서 스피커 캔버스 화면으로 간다.
2. "Add 3D Speaker"를 두 번 탭해 CH1, CH2 스피커를 만든다.
3. 3D 장면이 준비되기를 기다린다(`threeJsEngineProvider.isEngineReady`).
4. WebView의 `SpeakerBridge` 채널로 CH2 노드 탭 메시지를 보낸다: `{"type":"SPEAKER_SELECTED","speakerId":<CH2 id>}`.
5. CH2의 `SpeakerInspectorPanel`이 위젯 트리에 생긴다(`findsOneWidget`). 이 패널은 `_selectedInspectorSpeakerId`가 있을 때만 그려지므로, 이 단계 없이는 슬라이더와 서브 스위치를 찾을 수 없다.

### 3. 스피커 이동 → FX 반영

1. 200Hz 루프를 틀어 둔다.
2. CH2 인스펙터의 X/Y 슬라이더로 CH2를 청취 지점에서 멀리 옮긴다.
3. 다음을 확인한다.
   - CH2 튜닝의 게인과 딜레이가 바뀐다.
   - CH2 피크가 게인 변화만큼(±1dB) 바뀐다.

### 4. 서브 라우팅

1. JS 채널로 CH1 노드 탭 메시지를 보내 CH1 인스펙터를 연다.
2. "Set as LFE Subwoofer" 스위치를 켠다.
3. 각 채널 피크를 그 채널 튜닝 게인으로 나눠 정규화한 뒤 비교한다.
   - 200Hz 재생 중: CH1이 CH2보다 20dB 이상 작다. LR24 이론 차이는 약 32dB다.
   - 50Hz 재생 중: CH1이 CH2보다 10dB 이상 크다. LR24 이론 차이는 약 16dB다.

### 5. 재시작 복원

**자기 재시작 경로**

1. 20초 50Hz 트랙과 20초 200Hz 트랙을 함께 튼다.
2. 약 6초 뒤 다음을 기록한다: 트랙별 재생 위치, CH1·CH2 피크(0.5초 평균).
3. 결함 주입 훅으로 엔진 스스로의 재시작을 일으킨다(6절). 워치독과 같은 경로다.
4. 새 엔진이 준비됐다는 재시작 이벤트가 온 뒤부터 재개 전까지, CH1·CH2 피크는 "무음"이다. 이벤트 전에는 옛 엔진이 마지막으로 적은 피크 값이 남아 있을 수 있어 보지 않는다.
5. 재개 뒤 다음을 확인한다.
   - 두 트랙이 다시 재생된다. 재생 목록에 두 트랙이 있고 옛 인스턴스 항목은 남아 있지 않다.
   - 재개 뒤 측정한 트랙별 재생 위치 p1과 기록한 위치 p0에 대해 `p0 ≤ p1 ≤ p0 + (기록부터 측정까지 흐른 시간) + 0.5초`다. 멈춘 지점부터 이어 트는 것(R2)도, 재시작 시간만큼 앞으로 간 것도 이 범위에 든다. p1이 3초 미만이면 처음부터 다시 튼 것으로 보고 실패한다.
   - CH1·CH2 피크가 재시작 전 기록과 ±1.5dB 안이다. 서브 라우팅이나 3단계에서 바뀐 CH2 게인이 복원되지 않으면 여기서 어긋난다.

**재기동 창 안의 명령** (세대 확인 검사)

엔진 세대를 올린 뒤 옛 엔진이 drop되기까지는 길어야 100ms다. 이 창에 도착한 명령을 옛 엔진이 가져가면 안 된다.

1. `apiStopAudioEngine`(세대만 올림)을 부른다.
2. 곧바로 200Hz 루프 재생 명령을 보낸다.
3. `apiInitAudioSystem(null)`을 부른다.
4. 그 트랙이 새 엔진에서 재생되는지(CH2 피크) 확인하고, 그 트랙을 정지한다.
5. 1~4, 즉 **재시작 사이클 전체를 5번** 반복한다. 한 재시작 안에서 100ms 구간을 여러 번 샘플링하는 것이 아니다. 한 번의 재시작에서 옛 엔진이 drop되는 순간은 한 번뿐이라, 그 구간을 다시 겨누려면 재시작을 다시 해야 한다.

세대 확인이 있으면 매번 통과한다. 세대 확인이 없으면, 옛 콜백(약 42ms 주기)이 drop(엔진 스레드가 0~100ms 안에 세대를 봄) 전에 한 번이라도 돌아 명령을 가져갈 확률이 회당 약 79%다. 그래서 5번 중 한 번 이상 실패할 확률은 1 − 0.21⁵ ≈ 99.9%다. cpal 0.16에서는 옛 엔진이 곧바로 drop되므로 이 구간을 확정적으로 겨눌 방법이 없다. 확정적인 검사는 Rust 단위 테스트 `test_stale_engine_generation`이 맡는다.

### 6. 테마 시작

1. 대시보드 "Start"를 탭한다.
2. 첫 방의 루프 트랙(200Hz, 50Hz 2초 루프)이 재생 목록에 들어간다.
3. 5초 동안(루프 2바퀴 이상) 16ms마다 본 CH1·CH2 피크가 한 번도 문턱 아래로 떨어지지 않는다. 문턱은 각 채널 정상 레벨보다 6dB 낮은 값이다.
4. 같은 기간에 스트림 상태 `WatchdogActive`·`HotReloading`이 오지 않는다.
5. "Emergency"를 탭하면 무음이 된다.

VU는 블록 단위 피크라, 이 검사는 한 블록(약 42ms) 이상의 끊김을 잡는다. 샘플 단위 이음매 클릭은 Rust 단위 테스트가 맡는다.

## 6. 재시작 재생 복원 (신규 기능)

### 요구 사항

- **R1.** 엔진이 스스로 재시작하면(워치독 콜백 공백 1초, 장치 오류·재설정, 장치 목록 변화) 재시작 직전에 재생 중이던 트랙을 새 엔진에서 자동으로 다시 튼다.
- **R2.** 멈췄던 커서부터 튼다. 재시작하는 동안 소리가 없었으므로 그 시간만큼 앞으로 건너뛰지 않는다.
- **R3.** 서브 라우팅과 채널 FX는 재개되는 소리보다 먼저 복원된다. 기본값 FX로 소리가 나는 구간이 없어야 한다.
- **R4.** 재생 목록(엔진 상태 스트림)은 재시작 뒤에도 실제 재생과 일치한다.
- **R5.** 3법칙을 지킨다.
  - 오디오 스레드는 할당·잠금 없이 원자 슬롯에 커서만 적는다.
  - 재개는 기존 재생 페이드 인을 거친다(딸깍 소리 없음).

### 구조

1. **커서 게시.** 믹서가 블록마다 재생 중인 인스턴스의 (instance_id, 커서)를 `GLOBAL_STATE`의 고정 크기 원자 슬롯에 적는다. 인스턴스가 끝나면 슬롯을 비운다. 슬롯은 엔진 밖(`GLOBAL_STATE`)에 있으므로 옛 엔진이 사라져도 남는다.
2. **스냅샷.**
   - **시점:** 엔진 스레드의 감시 루프(`api_init_audio_system`, simple.rs 924행 `loop`)가 자기 재시작 사유로 루프를 빠져나오는 바로 그 지점이다. 사유는 `device_needs_reset`, `DeviceNotAvailable`, 콜백 공백 1초 초과, 장치 목록 변화다. 스냅샷은 `drop(engine)`보다 먼저, 그리고 새 엔진이 슬롯을 덮어쓰기 전에 뜬다.
   - **세대가 바뀌어서 빠져나온 경우**(사용자 정지·재기동)에는 스냅샷을 뜨지 않는다.
   - **읽는 것:** `playing_track_ids`(인스턴스 → 트랙)와 커서 슬롯. 이것으로 (room_id, track_id, 커서) 목록을 만든다.
   - **복원 위치:** 콜백이 멈춰서 재시작하는 경우에는 마지막으로 게시된 커서가 곧 멈춘 지점이다. 콜백이 아직 도는 경우에는 결정부터 drop까지 옛 엔진이 한 블록(약 42ms) 정도 더 재생할 수 있다. 그래서 재개 위치는 실제 마지막 출력보다 최대 한 블록 앞일 수 있다.
3. **목록 정리.** 스냅샷을 뜬 뒤 옛 인스턴스 항목을 재생 목록에서 지운다. 옛 믹서는 drop될 때 GC 스레드를 거치지 않아서, 지우지 않으면 화면에 재생 중으로 남는다.
4. **재동기화 뒤 재개.**
   1. 새 엔진이 준비되면 Rust가 Dart에 재시작 이벤트를 보낸다.
   2. Dart는 `resyncEngineStateToBackend`(서브 라우팅, 채널 FX, 리버브, 팬, 베이스 설정)를 실행한 뒤 "재동기화 완료"를 Rust에 알린다.
   3. Rust는 스냅샷의 트랙을 커서 위치부터 재생한다.
   4. Dart 응답이 2초 안에 없으면 그대로 재개한다. 무음보다 낫기 때문이다.
5. **재생 위치 조회 API.** 재생 중인 트랙별 위치(초)를 돌려준다. 1번의 커서 슬롯을 읽는다. 통합 테스트가 쓰고, 나중에 화면 진행 표시에도 쓸 수 있는 읽기 전용 API다.
6. **결함 주입 훅.** 장치 오류 경로가 세우는 신호(`device_needs_reset`)를 세워, 워치독과 같은 자기 재시작 경로를 그대로 탄다. 릴리스 바이너리에는 들어가지 않는다(아래 "결함 주입 훅의 릴리스 비노출").

### 재개 대기 구간(최대 2초)의 출력

이 구간의 출력은 **디지털 무음**이다. 옛 DSP 상태의 소리도, 클릭도 없다.

1. **옛 엔진은 새 엔진보다 먼저 없어진다.** 새 엔진 스레드는 옛 엔진 스레드를 join한 뒤에 시작한다(simple.rs 831행). cpal 0.16에서 옛 스트림을 drop하면 AudioUnit이 정지·해제되고 콜백 클로저(옛 믹서와 DSP 상태 포함)가 풀린다. 이것은 `test_engine_drop_releases_stream`이 보장한다. 그래서 옛 DSP로 소리가 날 수 없다.
2. **새 엔진은 빈 믹서로 돈다.** 재생 인스턴스가 없으니 믹서 입력이 0이다. 그 사이에 Dart 재동기화 명령이 DSP 값(EQ, 게인, 딜레이, 리버브)을 바꿔도 입력이 0이라 출력도 0이다. 새 엔진은 부팅 뮤트 램프에서 시작한다.
3. **재개는 페이드 인으로 시작한다.** 재개한 인스턴스는 `fade_weight` 0에서 시작해 샘플마다 올라간다(`player.rs` 296행, `mixer.rs` 667행). 커서가 파형 중간이어도 계단이 생기지 않는다.

5단계는 "재시작 이벤트 후 재개 전까지 무음"을 확인한다.

이 구간 **앞**에서 옛 출력이 끊기는 순간은 이 기능이 바꾸지 않는 기존 동작이다(10절 "알려진 한계").

### 재생 위치 읽기의 논블로킹

DSP 2법칙(오디오 스레드 블로킹 금지)을 지킨다.

- **오디오 스레드(쓰는 쪽):** 슬롯마다 원자 저장만 한다. 잠금, 대기, 할당이 없다.
- **조회 API(읽는 쪽, FFI 스레드):** 원자 값을 읽는다. 슬롯이 다른 인스턴스로 재사용되는 순간에 걸려 (instance_id, 커서) 짝이 섞일 수 있다. 그래서 커서를 읽은 뒤 슬롯의 instance_id(또는 슬롯 순번)를 다시 확인하고, 바뀌었으면 다시 읽는다. 다시 읽는 것은 읽는 쪽뿐이다. 오디오 스레드는 읽는 쪽을 기다리지 않는다.
- **인스턴스 → 트랙 대응(`playing_track_ids`):** RwLock이지만 오디오 스레드는 이것을 만지지 않는다. 쓰는 곳은 재생 API 스레드와 GC 스레드다.

### 결함 주입 훅의 릴리스 비노출

- **FRB 공개 API가 아니다.** 결함 주입은 `rust/src/api/`(FRB가 바인딩을 만드는 공개 표면)에 두지 않는다. 별도 모듈의 C 심볼(`#[no_mangle] extern "C"`)로 만들고 `#[cfg(debug_assertions)]`로 막는다.
- **릴리스·프로파일 빌드에서는 컴파일되지 않는다.** cargokit은 Flutter debug 빌드만 `--release` 없이 빌드하고, profile·release 빌드는 `--release`로 빌드한다(`rust_builder/cargokit/build_tool/lib/src/builder.dart` 27~29행, 162행). `--release`에서는 `debug_assertions`가 꺼지므로 심볼이 아예 없다.
- **앱 코드는 이 심볼을 부르지 않는다.** 통합 테스트 파일만 `dart:ffi`로 Rust 라이브러리에서 심볼을 찾아 부른다. 그래서 릴리스 앱에서 심볼이 없어도 앱은 영향을 받지 않는다.
- **검증:** 릴리스 빌드의 Rust 프레임워크에 이 심볼이 없는지 `nm`으로 확인한다(9절).

### 채택하지 않은 방식

Rust가 마지막 상태 명령을 모두 기억했다가 새 엔진에 다시 넣는 방식(상태 일지)도 있다. Dart 없이 복원되는 장점이 있지만 채택하지 않았다.

- 명령마다 덮어쓰는 범위를 Rust에 한 번 더 구현해야 한다.
- 프로젝트를 바꿀 때 일지를 비우는 규칙이 필요하다.
- 결과적으로 상태의 진실 공급원이 둘이 된다. 지금은 Dart 상태가 유일한 기준이고, 재기동 복원 함수(`engine_resync.dart`)도 이미 있다.

### EngineReady 폴링 누락

지금 워치독 복구 뒤의 재동기화는 `main.dart`가 `EngineReady`를 받아 처리한다. 그런데 이 신호는 준비 상태를 500ms마다 봐서 "준비 안 됨 → 준비됨"으로 바뀔 때만 나간다. 재기동에서 준비 안 된 구간이 더 짧으면 놓칠 수 있다(가설).

위 4번의 명시적 재시작 이벤트가 자기 재시작 경로에서는 이 폴링을 대신한다. 5단계에서 폴링 누락이 드러나면 원인을 확인하고 함께 고친다.

## 7. 앱 코드 변경

- **위젯 키.** 테스트가 찾을 위젯에 키를 단다: 방 카드 트랙 재생/정지, 대시보드 Start·Emergency, 스피커 캔버스로 가는 버튼, 인스펙터 X/Y 슬라이더, LFE 스위치. 동작은 바뀌지 않는다.
- **6절 기능, Rust.** 커서 게시, 스냅샷, 재개를 추가한다. 재생 위치 조회 API는 FRB 공개 API로 추가하고, 이 때문에 FRB 바인딩을 다시 생성한다. 결함 주입 훅은 FRB 밖의 디버그 전용 C 심볼이다.
- **6절 기능, Dart.** 재시작 이벤트를 받아 재동기화하고, 완료를 Rust에 알린다.
- **삭제.** `integration_test/simple_test.dart`를 지운다. flutter_rust_bridge 템플릿 잔재("Hello, Tom!")라 실제 앱을 검증하지 않는다.
- **개발 의존성.** 가짜 path_provider에 필요한 `path_provider_platform_interface`, `plugin_platform_interface`를 dev 의존성으로 추가한다.

## 8. 실행과 안전

- 명령은 `flutter test integration_test/app_flow_test.dart -d macos`다.
- 실행 전에 다른 앱 인스턴스가 없어야 한다(테스트가 확인한다). 빌드용 디스크 여유는 3GB 이상을 권장한다.
- 시스템 기본 출력 장치로 −30dBFS 톤이 실제로 나온다.
- 목표 소요 시간은 3분 이내다.
- 수동 실행만 하고, CI에는 넣지 않는다. macOS 전용이다.

## 9. 성공 기준

1. 이 Mac에서 3회 연속 통과한다.
2. 아래 변경을 하나씩 되돌리고 실행하면, 해당 단계에서 그 단계를 가리키는 메시지로 실패한다.

|---|---|
| FX 자동 동기화 watch 제거(`main.dart` `acousticSyncProvider`) | 3 |
| 서브 지정을 공간 설정 payload에서 빼기 | 4 |
| 재시작 재생 복원 전체 제거 | 5(재개 없음) |

## 10. 알려진 한계

이 테스트가 보장하지 않는 것이다. 나중에 이 테스트가 통과했다고 해서 아래까지 보장된다고 오해하지 않도록 적어 둔다.

- **3D 장면의 클릭 판정.** 테스트는 `speakerId`를 직접 골라 `SpeakerBridge` 채널에 `SPEAKER_SELECTED`를 넣는다. 그래서 Three.js가 레이캐스팅으로 어느 노드를 탭했는지 알아내는 JS 쪽 히트 테스트는 검증하지 않는다. 검증 범위는 JS 채널부터 Dart까지다.
- **재시작 순간 옛 출력이 끊기는 것.**
  - 워치독 재시작은 콜백이 이미 멈춘 뒤라 장치가 이미 조용하다.
  - 장치 재설정이나 장치 목록 변화로 재시작할 때는 옛 엔진이 소리를 내던 중에 drop되어 출력이 바로 끊긴다(기존 동작).
  - 이 끊김을 페이드 아웃으로 바꾸는 것은 이번 범위가 아니다.
- **재동기화 대기 타임아웃 뒤의 재개.** Dart가 2초 안에 재동기화를 끝내지 못하면, 서브 라우팅과 FX가 기본값인 채로 재개될 수 있다(R3의 예외). 무음보다 낫다고 보고 택했다.
- **VU의 시간 해상도.** 출력 피크는 오디오 블록(약 42ms) 단위다. 그보다 짧은 끊김이나 샘플 단위 클릭은 이 테스트가 못 잡는다. Rust 단위 테스트가 맡는다.
- **엔진 세대 확인의 통합 검사는 확률적이다**(약 99.9%, 5단계).
- **플랫폼.** macOS 실기 전용이다. Windows(ASIO/WASAPI)의 같은 흐름은 검증하지 않는다.

| 위험 | 대응 |

## 12. 계획 단계에서 정할 것

- **스트리밍 트랙(`is_streaming`)의 커서 복원.** 선택지는 두 가지다. (a) `DiskStreamer`에 시작 위치 시크를 추가한다(symphonia seek). (b) 이번에는 미리 로드한 트랙만 커서를 복원하고 스트리밍은 처음부터 튼다(한계로 기록). 판단 기준은 시크 위치가 포맷별로 샘플 단위까지 정확한지다.
- **커서 슬롯.** 크기, 형식, 스냅샷에서 room_id를 얻는 방법(재생 목록에 방을 같이 담을지, 설정에서 찾을지).
- **Dart ↔ Rust 신호.** 재시작 이벤트와 재동기화 완료 신호의 형태(기존 스트림에 이벤트 추가인지, FFI 함수인지). 대기 타임아웃은 6절의 2초로 시작한다.
- **결함 주입 심볼을 테스트에서 찾는 방법.** FRB가 쓰는 것과 같은 Rust 프레임워크를 `DynamicLibrary`로 열어 찾는다. 경로와 방식은 FRB의 로더를 보고 정한다.
- **픽스처 config.json 생성 방식.** 기본 설정을 받아 수정 후 저장할지, JSON을 직접 쓸지.
- **세부 값.** 위젯 키 이름, VU 문턱과 측정 창(시험 실행으로 보정).
